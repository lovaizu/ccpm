# first user の報告：writ/docs/design.md

行番号の表記：「設計 N」= writ/docs/design.md、「README N」= writ/README.md、「doc N」= references/essentials/doc.md、「des N」= references/essentials/design.md、「ess N」= references/essentials/essentials.md。

## 使った立場と、したこと

読み手と目的から、私（これから writ のプロンプト・エージェント・スクリプトを作り、あとで保守する人）が読み終えて決め、することを次のように定めた。

- 決めること：何を作るか（スキル、エージェント、hook、スクリプト、テスト、lint の設定）と、それぞれの作り方。ありそうな変更が設計に合うか。
- すること：作り始め、ベネフィットごとの確かめを走らせる。

README を先に読み（README 1-183）、そのあと設計書を上から一度通して読んだ。実装はまだないので読んでいない。des 3 の求めに従い、ありそうな変更を2つ選んだ。

- 変更A：pith が結果のファイルを書かず、全文を呼び出し元に返すようにする。
- 変更B：生成者をやめ、`/writ:up` の指揮者が自分で文書を書くようにする。

ベネフィットは「報告で判断できる」を1つ選んで確かめ方を組もうとした。

## どの文書にも（doc.md）の問いへの答え

### doc 5：読み終えて、何を決め、何をすると受け取ったか

作るものとして次を受け取った。

- スキル2つ：`/writ:up`（設計 3）と pith（設計 3、284 で `context: fork`）。
- プラグインのエージェント2つ：生成者と first user（設計 75）。first user に `omitClaudeMd`、生成者の道具からほかのエージェントを呼ぶ道具を外す（設計 75）。
- hook：first user が動いている間だけ、git の履歴・会話の記録・前の版を読む道具の使い方を止める（設計 300-302）。
- スクリプト：pith の中に置き、すべての観点に答えがあるか、場所が実在するか、引いた根拠が成果物にあるかを確かめる（設計 312-314）。unittest で止める例と通す例（設計 372-373）。
- 書き方の決まりのファイル（観点とは別）と、Vale と textlint を npx で決まった版で動かす設定（設計 114-116）。
- スキルの説明に「作業の途中で文書を書こうとするときにも使う」と書く（設計 258）。
- 結果のファイル `.writ/open/{NN}-report-{対象}.md`（設計 83）。

すること（確かめ）として、6つのベネフィットを README の場面で1回ずつ動かすこと（設計 337-365）と、4つのスクリプト確認（設計 371-374）を受け取った。

決めることとして、変更Aは合わない、変更Bも合わないと決めた（下の des 5 に詳しく）。

### doc 13：書いてなく、推し量るか聞くしかなかったこと

- pith を利用者が直接呼ぶときのスキルの名前。README 121・144 は「pith で…」と言葉で頼んでおり、設計 246 は名前として「pith」を挙げるが、`/writ:pith` のような呼び名かどうかは書いていない。
- 指揮者が、文書の種類に応じてどの観点ファイルを選ぶか。設計 215 に「観点を選ぶところから」とあるが、選ぶ手順・基準はどこにもない。README 155-160 から「doc.md はいつも、種類ごとのファイルを足す」と推し量った。
- 書き方の決まりのファイルの置き場所と名前（設計 114-116 は「別のファイルに置きます」とだけ）。
- 結果のファイルの中の形（見出し、場所の書き方、根拠の引き方）。スクリプト（設計 312）が「場所が実在するか」「引いた文が成果物にあるか」を機械で確かめるには形が決まっている必要があるが、どう書くかはない。`{NN}` の付け方もない（設計 83）。
- pith が観点を作るとき（設計 320-333）、生成者を pith の指揮者が呼ぶのか。設計 5-29 の図では生成者は pith の枠の外にあり、`/writ:up` の指揮者からしか矢印がない。pith の指揮者が生成者を呼ぶ形と推し量った。観点を作るときも結果のファイルを書くのかも書いていない。
- 直すたびに生成者を新しく呼ぶのか、同じ生成者に続けて頼むのか。設計 193「生成者は確かめた結果を知らない」から、毎回新しく呼ぶ形と推し量った。
- hook が止める「前の版を読む」の具体（設計 302）。git の操作なのか、別の場所にある古いファイルなのか。
- 「狙い」の書き方（設計 130 は「読み手が得るべきものと、利用者と決めたこと」）を、pith の指揮者が観点を覆っているかを確かめる（設計 288）ために、観点ごとに書かせるのかどうか。
- 呼び出し元（rn など）が結果のファイルの場所を指定する方法（設計 83、310）。`/writ:up` にどう渡るのか。

## 設計書（design.md）の問いへの答え

### des 5：ありそうな変更が設計に合うかを、利用者が何を失うかからどう決めたか

変更A（結果のファイルを書かず全文を返す）：

- 触れる機能を探した。「観点ごとの最後の Good・More を返す」（設計 51-53）が「報告で判断できる」に仕えると分かった。
- 設計 221「全部を会話に載せると…報告が長くなりすぎて読まれません」、設計 308-310「全文を返すと、呼び出し元の会話がそれで埋まります」、設計 83「会話が長くなって要約されても全文が残り」を見つけた。
- 利用者が失うもの：報告だけで判断できなくなること（README 7）と、要約で全文が消えること。合わないと決めた。

変更B（指揮者が自分で書く）：

- 設計 104「指揮者が自分で書く形は選びません。…書いて直すたびに利用者との会話が長くなり、要約されて決めたことの細部が抜けやすくなる」を見つけた。
- 利用者が失うもの：決めたことが抜けた文書になり、「そのまま渡せる」（README 6）が崩れる、と受け取った。設計 104 は失うものを「決めたことの細部が抜けやすくなる」までで述べ、どのベネフィットが崩れるかは、この機能が仕える「一度読めば分かる」「そのまま渡せる」（設計 37）から私がつないだ。合わないと決めた。

### des 9：迷ったとき、どの方針を思い出して使ったか

方針は設計 69-83 の4つで、覚えていられた。

- 変更A では「最後に残るのは対象の成果物だけ。結果のファイルは、片付くまで `open/` に置く」（設計 81-83）を使った。
- 変更B では方針ではなく、機能の節の中の決まり（設計 102-104）を使った。方針の「判断するのは指揮者だけ」（設計 69-71）も思い出したが、変更B は判断ではなく書く役の話なので、直接は使わなかった。

### des 13：使った方針について、守らなければ何が壊れると受け取ったか

- 設計 81-83：守らないと、下書きが残って利用者が片付けることになりどれが本物か迷う、全文が会話に流れ込む、要約で全文が消える、`open/` が「対応が要る」という印にならない、と受け取った。README 92 とつながっていると受け取った。
- 設計 69-71（参考に読んだ）：守らないと、話し合いを知らない役が目的に役立つ所まで作り直す、生成者の採点が甘くなる、と受け取った。どのベネフィットが壊れるかは書いておらず、私は「そのまま渡せる」につないだ。
- 設計 73-75：守らないと、first user に話し合いが届く、と受け取った。これで何のベネフィットが壊れるかは書いておらず、README 38、135 から「一度読めば分かる」「使った事実で確かめられる」につないだ。
- 設計 77-79：守らないと、写しがずれて生成者のめざす形と first user の答える問いが離れる、と受け取った。

### des 17：README のベネフィットそれぞれを、どの機能で得ると受け取ったか

設計 33-65 から次のように受け取った。

- 一度読めば分かる（README 5）：読み手と目的を決めてから書かせる（設計 35）、pith で first user に使わせて確かめる（設計 39）。
- そのまま渡せる（README 6）：上の2つと、直せる穴は直し残せる穴は理由を付けて残す（設計 43）。
- 報告で判断できる（README 7）：直せる穴は直し…（設計 43）、観点ごとの最後の Good・More を返す（設計 51）。
- ごまかさずに聞かれる（README 8）：目的を妨げる穴は、ごまかさずに利用者へ聞く（設計 47）。
- 使った事実で確かめられる（README 12）：受け手として使った事実を、狙いと比べて Good・More にする（設計 59）。
- 目的から逆算した観点を作れる（README 13）：観点を目的から逆算して書き、実物で試す（設計 63）。
- 作業の途中で書く文書も同じ流れで仕上げる（設計 55）は、上の4つを `/writ:up` を呼ばなかった文書に届けるものと受け取った。

どのベネフィットにも機能があった。

### des 21：選んだ変更の後も、いつも成り立っていなければならないと受け取ったこと

- 変更A について：「`open/` には片付いていないものだけが残る」（設計 83）、作業のあと変わったのは対象の成果物と `open/` の結果のファイルだけ（設計 371）。
- 変更B について：生成者に渡すものは、話し合いに戻らなくても意図どおり書ける量（設計 104）。ただしこれは生成者がいる前提の決まりで、変更B では対象が消える。
- どの変更でも：観点の中身は観点ファイルにだけある（設計 79「どの変更のあとも」）、対象の文書は中身の穴をぼかさない（設計 209「どの状態のあとも」）、利用者が目にする名前は変えない（設計 244-248）。

### des 25：ベネフィットを一つ確かめようとして、何が起きれば通ったと受け取ったか

「報告で判断できる」を選んだ。設計 351-353 から、確かめる人が報告だけを読んで承認するかどこを直すかを決め、そのあと文書全体を読んでも判断が変わらず、どの Good・More がどの観点への答えかが報告だけで分かれば通る、と受け取った。

### des 29：その確かめを、どんな場面で走らせると受け取ったか

README 40-92 の移行計画の場面（残した More が承認の判断を左右する）と受け取った（設計 353）。設計 337 の「ベネフィットがなければ利用者がはっきり困る場面」を、この場面が満たすと受け取った。場面ごとに1回動かす（設計 339）。

### des 33：確かめる手間を、どこにかけると受け取ったか

- まず6つのベネフィットを、ゴールデンパスの場面で（設計 337）。ベネフィットが通るまで当たり前品質を先に直さない。
- 機械で決められる4つはスクリプトで毎回（設計 369-374）。
- それ以外の当たり前品質は前もって確かめず、出てきたら直す（設計 376）。
- ほかの種類の成果物・読み手、Claude Code が writ を選ぶかは動かして確かめず、スキルの説明を公式の手引きと照らして読む（設計 380-382）。

### des 37：今のやり方を別の案に替えたくなった所で、なぜ今のやり方が選ばれたと受け取ったか

- 生成者と first user をプラグインのエージェントにする（設計 75）：以前は直接呼べてしまうことを理由に避けたが、守りたいのは話し合いが届かないことで、`omitClaudeMd` を付けられるのは定義だけだから、と受け取った。
- 指揮者が自分で書かない（設計 104）：会話が長くなり要約で細部が抜けるから。
- 作業の途中の文書で hook や CLAUDE.md を使わない（設計 258）：hook は中身ができてから動き、作業メモでも動く。CLAUDE.md は利用者の環境に残り保つ手間を移す。
- 書き方の決まりを観点と別のファイルにする（設計 116）、pith に渡さない（設計 134-136）。
- 当たり前品質の More を確かめ直さない（設計 140）。
- pith を `context: fork` で動かす（設計 284-286）。
- 替えたくなって理由を探したが見つからなかった所：pith の指揮者を、first user と同じエージェントでなく fork したスキルにしている理由（設計 284-286 は「会話を引き継がない」理由で、スキルかエージェントかの理由ではない）。`/writ:up` と pith を2つのスキルに分けた理由（設計 3 は分けたことだけ）。

- 設計 266-280 の図：設計 284-318 と、README 135-137 の言い直し。

- 設計 343-365 の各項の一文目（「読み手は一度読めば分かり…」など）：README 5-13 の言い直しだが、各項の見出しとして使った。
- 設計 237-242：README 69、90 と一部重なるが、項目ごとの理由（なぜその項目があるか）は README になく、変更A の判断に使った。

### des 45：選んだ変更を入れたとして、意図は変わらないのに書き直すことになる文

- 変更A を、例えば結果のファイルの置き場所だけ変える形に弱めた場合：設計 83 の `.writ/open/{NN}-report-{対象}.md`、設計 371 の `open/` が書き直しになる。
- 設計 75 の `omitClaudeMd`、設計 284 の `context: fork`、設計 116 の Vale・textlint・npx は、Claude Code の設定の名前や道具の名前で、道具を替えると意図は同じでも書き直しになる、と受け取った。
- 設計 372-373 の「Python の unittest」も同じ。

### des 49：利用者の環境に残り、後の版や人が読むものの形を変えようとしたとき

「結果のファイル」と「片付けのコミットメッセージ」を、利用者の環境に残り、利用者・rn・後の版が読むものと受け取った。項目を1つ削れるかを考えた。

- 結果のファイルの項目：観点ファイルの名前、場所、根拠、Good の得るもの、More の困ること、More の残した理由（設計 235-242）。それぞれ、利用者が何に使うかが書いてあり、削ると何が読めなくなるかが分かった。どの項目も削れないと受け取った。
- いつも成り立つこと：`open/` には片付いていないものだけ（設計 83）、対象ごとに1つで上書き（設計 83）。
- 形：ファイル名の形は設計 83 にある。中の形（見出し、場所や根拠の書き方）はない。そのため、rn のような呼び出し元がファイルの中を読むとき、どの書き方なら壊さずに変えられるかは決められなかった。
- コミットメッセージ：末尾の印 `→ fixed:`、`→ let go:` と理由、`→ to the user:`（設計 227）。印を変えると何が読めなくなるか（後から誰が何のために読むか）は、設計 229「選ばなかった道としてあとから読めます」から、人が読むものと受け取った。機械が読むかは書いていない。
- 利用者が目にする名前（設計 244-248）も変えられないと受け取った。

### ess 15：問いごとに、どんな答えが出たか

- 設計書のどの文が何に使われたか、使われなかったか、という答えが出た問い：doc 9、des 41、des 45。
- 記述の性質（事実か決定か）の答えが出た問い：doc 33。
- 一文を読んだ時点の受け取りだけが出た問い：doc 21。
- 方針とその理由の答えが出た問い：des 9、des 13、des 37。

### ess 25：使った部分と通り過ぎた部分は、どの問いの答えに出たか

- doc 9 の答えに、使った行範囲と読み流した行（設計 128、282、266-280 ほか）が出た。
- des 41 の答えに、README と重なって判断に使わなかった文が出た。doc 9 の読み流した部分と重なった（設計 128、266-280、282）。
- des 45 の答えに、道具の名前で書かれた文（設計 75、116、284、372-373）が出た。これは使った部分の中の、書き直しになる所として出た。
- doc 13 と des 37 の答えには、使おうとして見つからなかった所（書いていない所）が出た。

### ess 35：どの問いの答えが働き、どれが何の働きもしなかったか

読み手の目的（ベネフィットごとの機能と作りを知る、ベネフィットを確かめられる、変更が設計に合うかを言える）に向けて：

- 変更が設計に合うかを言うのに働いた：des 5、des 9、des 13、des 21、des 37、des 49。des 5 の答えが中心で、des 9・13・21 はその判断の中で使った方針と理由を分けて出した。
- 機能と作りを知るのに働いた：des 17、doc 5、doc 13、doc 17、doc 29。doc 13 と doc 17 は、作り始めるのに要るのに見つからなかったもの（pith の呼び名、観点の選び方、結果のファイルの中の形、観点を作るときの生成者の呼び手）を出した。
- ベネフィットを確かめるのに働いた：des 25、des 29、des 33。
- 何の働きもしなかった、またはほかの答えと重なった：doc 21（一文目の受け取りは、続けて読んだ doc 5 の答えに含まれた）。doc 25 は、見出しから hook と lint が探せなかったことを出したが、作るものと判断には影響しなかった。des 41 は doc 9 と同じ行を出した。doc 33 は、設計 302 の前提を事実として受け取ったことを出したが、それで何かを決め直したわけではない。

### ess 45：一つの答えで二つ以上の点に答えた問い

- des 5：変更を選ぶことと、合うかを利用者の失うものから決めることの2つを答えた。
- doc 9：使った部分と、読み飛ばした部分の2つを答えた。
- doc 17：止まった所と、そこで分からなかったことの2つを答えた。
- des 49：どの項目を変えられるかと、そのために何を見たか（理由・いつも成り立つこと・形）を答え、形については「中の形がない」という別の点も一緒に答えた。
- des 37：理由が書いてあった所と、替えたくなって理由がなかった所の2つを答えた。

### ess 55：問いの言葉だけでは何を確かめるか決まらなかったとき、何を手がかりにしたか

- des 3・des 41・des 45：「README と実装と一緒に受け取り」「README と実装を読んだうえで」とあるが、実装はない。README だけと比べた。手がかりは、依頼で「実装はまだない」と言われたこと。
- des 5：「ありそうな変更」は自分で選んだ。手がかりは des 7 の「機能ごとに、それが仕えるベネフィット…が見つかれば」で、機能とベネフィットにつながる変更を選んだ。
- des 21：「いつも成り立っていなければならない」を、des 23 の「どの操作の後にも成り立つ条件」を手がかりに、設計書の「どの変更のあとも」「どの状態のあとも」の文から拾った。
- des 49：「利用者の環境に残り、後の版や人が読むもの」が何かは、des 51「外との約束」「役どうしの受け渡しは、外との約束ではありません」を手がかりに、結果のファイルとコミットメッセージを選び、生成者や first user への受け渡しは外した。
- doc 5：何を決め何をするかは、依頼の読み手と目的から定めた（doc 3）。

## 指揮者の Good・More

狙い: 作る人が、ベネフィットごとの機能と作りを知り、作り始められ、変更が設計に合うかを言える。

- Good: 機能とベネフィットの対応（31–65）。6つすべてに機能が当たった（des 17）。
- Good: 変更が合うかを言える。変更A・B とも、利用者の失うものから「合わない」と決められた（des 5・9・13）。
- Good: ほぼ全体が作るのに使われ、読み流されたのは 128、282 の2文目、33、266–280 の図、380–382 だけ（doc 9）。
- More: pith の呼び名（`/writ:pith`）がない（doc 13）。
- More: 文書の種類から観点ファイルを選ぶ決まりがない（doc 13）。
- More: 結果のファイルの中の形（見出し、場所と根拠の書き方、`{NN}`）がない。スクリプトも rn もこの形を読むので外との約束（doc 13、des 49）。
- More: 観点を作るとき、生成者を呼ぶのが pith の指揮者だと図にも文にもない。結果のファイルを書くかもない（doc 13・17）。
- More: 直すたびに生成者を新しく呼ぶかがない（doc 13）。
- More: hook が止める「前の版を読む」が何か分からない（doc 13）。
- More: 狙いを観点ごとに書くのかが分からない（doc 13）。
- More: 呼び出し元が結果のファイルの場所を `/writ:up` にどう渡すかがない（doc 13）。
- More: 「魅力的品質」「当たり前品質」が説明（335 以降）より前の 138 に出る（doc 17）。
- More: 状態図の「決める」に、いつも戻るのか分からない（doc 17）。
- More: pith を fork したスキルにした理由と、スキルを2つに分けた理由がない（des 37）。
- More: 302（hook の入力で分かる）と 75（omitClaudeMd）の出どころがなく、286 の「公式」がどれか分からない（doc 33）。
- More: 282 の2文目は 71 と重なる（doc 9）。140 の rn の経験は範囲がない（doc 33）。
- let go: 266–280 の図は AI の読み手には文の繰り返しだが、人の読み手には受け渡しの順が一目で分かる。
- let go: `omitClaudeMd`・`context: fork`・Vale・textlint・unittest は道具を替えると書き直しになる（des 45）が、どれも利用者と決めた設計の決定そのもの。
