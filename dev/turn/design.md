# turn の設計

この設計書は、turn を作る人と直す人のためのものです。[README](../../turn/README.md) の約束を、どの機能が利用者に届けるか、それをどう確かめるかを書きます。変更が設計に合うかは、下の方針に照らし、利用者が何を失うかで決めます。

turn の中で判断する役を、指揮者と呼びます。`turn:up` を動かしているメインの会話のことで、README で「判断するのは turn だけ」と書いているのは指揮者のことです。

## 1. 方針

指揮者は、作り手に作らせ、使い手に受け手として使わせ、学び手につまずきの元を学ばせ、その元から作り直させます。これを、使ってみた結果があるべき姿に合うか、残りが利用者やスキルにしか決められないことだけになるまでくり返し、受け手が実際に使える成果物にします。次の5つは、このくり返しが受け手の使える成果物にたどり着くために、いつも成り立っていることです。

- すべての判断の物差しは、CCS に書かれたあるべき姿です。

    あるべき姿は、プラグインが書く受け手（`receiver`）、合格の基準（`acceptance`）、何に使うか（`use`）、観点のファイル（`viewpoint`）です。ターンが知っていることは CCS だけなので、指揮者が自分で思い描いた姿は、次のターンにも続きにも渡りません。あるべき姿を決めるのはプラグインで、turn はそれを作りも変えもしません。そうでないと、利用者が合意していない基準で成果物が直され、「合格の基準や決まりが、タスクの途中で書き換わらない」が崩れます。あるべき姿だけでは判断できない時は、スキルに返します。

- 使い手は、受け手と同じ立場で使います。

    知らせるのは、成果物と、受け手が誰で何に使うかだけです。合格の基準や話し合いは知らせません。使う場所は、受け手の手元と同じ、クローンしたばかりの一時的な写しです。こうすると、使い手がつまずく所と受け手がつまずく所が同じになり、「見せられる成果物は、すでに使われ、つまずいた所が直っている」が本当になります。基準を知っていると、使い手はそれに沿って使ってしまいます。作業中のリポジトリには受け手の手元にないファイルがあり、それに助けられて、つまずきが隠れます。

- 直すのは、つまずきの元です。成果物は、そこから作り直します。

    つまずいた箇所だけを継ぎ足すと、元が残ったまま別の所で同じつまずきが起き、成果物はあるべき姿から離れていきます。元から作り直せば、使い直すたびにあるべき姿に近づきます。あるべき姿に近づかない直しはしません。見送るか、スキルに返します。

- 判断するのは指揮者だけです。指揮者は、報告の1つ1つを、あるべき姿と並べ、成果物と事実で裏を取ってから決めます。

    作り手、使い手、学び手は、それぞれ1つの仕事をして、したことと起きたことを報告するだけです。良し悪しは付けません。作った本人が確かめると甘くなり、判断がエージェントに散ると、どの直しがあるべき姿のためかを誰も言えなくなります。報告の言い分は、したこと以上を言いうるので、指揮者は会話の記録（JSONL）と git で裏を取ります。良いという報告も、つまずいたという報告も、学び手が出したつまずきの元も、同じ厳しさで裏を取ります。良いという言い分を信じると、つまずきがそのまま受け手に届きます。

- ターンが終わって残るのは、返す CCS と成果物だけです。

    次のターンは、それだけから始めます。会話の記録や、指揮者の頭の中には頼りません。受け取った CCS は書き換えず、新しい CCS を別のファイルに書きます。こうすると、CCS と成果物をコミットしておけば、途中で止めても、別のマシンでも続きから進み、ターンが途中で切れても同じ CCS で始めからやり直せます。プラグインも、返ってきた CCS だけで次の一手を決められます。

## 2. 機能

各機能が届ける約束は、README の「プラグインの作者にとって」と「プラグインの利用者にとって」の項です。働く場面は、README の「使う場面」と「返ってきた CCS で次を決める」です。

ターンの中で、指揮者がそれぞれのエージェントに渡すものと、受け取るものは次のとおりです。

| エージェント | 渡すもの | 受け取るもの |
|---|---|---|
| 作り手 | CCS に書かれたあるべき姿、資料、決まり、利用者の答え。直す時は、裏を取ったつまずきの元 | 作った成果物と、したこと |
| 使い手 | 成果物、受け手、何に使うか。クローンしたばかりの一時的な写し | したことと、起きたこと |
| 学び手 | 使い手の報告、その回の会話の記録、観点のファイル | つまずきの元。成果物についてのものと、進め方についてのもの |

### 受け手として使い、つまずきの元から直す

届ける約束は「見せられる成果物は、すでに使われ、つまずいた所が直っている」と「作って、使ってみて、直す流れを、自分のスキルに書かずに済む」です。

- 作り手が作ったら、指揮者はその都度、使い手に受け手として使わせます。

    作っただけで使わずに次へ進むと、使われていない成果物が受け手に届きます。

- 使い手が使い終えたら、指揮者はその都度、学び手につまずきの元を学ばせます。

    使い手の報告だけでは、どこでつまずいたかは分かっても、なぜつまずいたかは分かりません。学び手は、報告と、その回に実際に起きたことの記録から元を探します。

- 指揮者は、裏を取ったつまずきの元のうち、成果物についてのものを作り手に渡し、成果物をそこから作り直させてから、使い直させます。

    元から作り直すと、つまずいた箇所以外も変わりうるので、使い直しは始めからです。

- 進め方についての元は、決まり（`rule`）になります。指揮者はターンの残りで呼ぶどのエージェントにもそれを渡し、返す CCS の `constraints` に足します。

    スキルがそれを次のタスクの CCS に写せば、タスクをまたいでも同じつまずきをくり返しません。

- 使い直しても同じ元のつまずきが残る時は、元の見立てが違うか、あるべき姿では決められないことです。指揮者はそれを `to the caller` でスキルに返します。

    同じ直しをくり返しても、あるべき姿には近づかないからです。

- 使い手が使う写しは、使い終えたら消します。turn はコミットも push もしません。

    これで「利用者のほかの作業に触れない」が成り立ちます。コミットするかどうかは、利用者とタスクの並びを知るプラグインが決めます。

### 利用者にしか決められないことだけを返す

届ける約束は「聞かれるのは、利用者にしか決められないことだけ」です。

- CCS とその資料、利用者の答え、観点から決まることは、指揮者が決めます。
- 決まらず、利用者にしか決められないことだけを、そのまま聞ける問いにして `gap` に入れ、`next` を `ask the user` にして返します。

    turn は利用者と話しません。何をいつ利用者に聞くかは、利用者とタスクの並びを知るスキルにしか判断できないからです。

### 返す CCS だけで次を決められる

届ける約束は「成果物を読まずに、次の一手を決められる」です。

- 指揮者は、つまずきごとの結末（`difference`）、利用者にしか決められないこと（`gap`）、学んだ決まり（`rule`）、成果物と資料のつながり（`link`）、次にすること（`next`）を書きます。
- 各エージェントが実際に読み、書き、実行したこと（`episodic_trace`）は、ターンを返す前に、会話の記録と git から機械が書きます。

    エージェントの言い分は、したこと以上を言いうるからです。判断は指揮者が書き、事実は機械が書くので、両者は食い違いません。

### あるべき姿が途中で書き換わらない

届ける約束は「合格の基準や決まりが、タスクの途中で書き換わらない」です。

- CCS を受け取った時と返す時に、形を機械が確かめます。合わなければ、何が合わないかを言って止まります。何を確かめるかは、README の「機械が確かめること」のとおりです。

    AI が書く CCS は、あるべき姿の行を言い換えたり、表にない項目を足したりしうるからです。機械の確かめは、毎回同じ答えを出します。

- 確かめには python3 を、CCS の読み書きには jq を使います。どちらかがなければ、CCS を返さずに、何をインストールすればよいかを会話で伝えて止まります。

    確かめを飛ばして進むと、書き換わったことに誰も気づかないからです。

### 止めた所から続ける

届ける約束は「途中で止めても、続きから進む」です。

- 利用者が会話で止めるよう言ったら、指揮者は新しいエージェントを呼ばずに、報告を受け取り終えた所までを新しい CCS に書き、`next` を `stopped: <どこから>` にして返します。

    報告を受け取った回は、もう確かな事実です。失うのは、動いていた1回だけです。

- CCS を返さずに切れたターンは、何も書き残しません。スキルは同じ `in` でもう一度呼び、ターンを始めからやり直します。

    書きかけの CCS を頼りに続けると、半端な状態から進むことになるからです。受け取った CCS は元のままなので、やり直しはいつでもできます。

## 3. CCS の取り決め

CCS は、プラグインが書いて残し、turn が読み、次のバージョンの turn や別のマシンでも読まれます。形は README の「CCS の書き方」がすべてで、ここには、各部分がなぜあり、何がいつも成り立つかを書きます。

- CCS は、ACC の9つの部分をすべて持ち、ほかの部分を持ちません。

    9つの部分は、論文が次の一手に要る状態として決めたものです。部分を足すと、ACC と食い違い、読む側がそのたびに変わります。

- プラグインが書く部分（`focal_entities`、`goal_orientation`、`retrieved_artifacts`）は、タスクの間ずっと変わりません。

    これがあるべき姿だからです。

- `constraints` は、書かれた行が変わらず、後ろに足されるだけです。

    利用者の答えと、学んだ決まりは、一度決まったら後のターンでも守られるからです。

- turn が書く部分は、ターンごとに作り直されます。

    次の一手に要るのは、直前のターンの結果だけだからです。

- 成果物や資料の中身は書かず、場所だけを書きます。

    中身を写すと、写しと実物が食い違い、CCS が膨らみます。

- 部分と種類の名前、`next` の値は英語のままで、決まったものだけです。

    スキルが `jq` で読み、次の一手を決める鍵だからです。名前や値を変えると、それを読むスキルが次を決められなくなります。

## 4. 確かめ方

約束が利用者に届いているかを、まず試走で確かめます。試走は `dev/turn/trials/` に置き、利用者がするとおりに turn を動かして、すべての会話とエージェントの記録（JSONL）から判断します。

- 「見せられる成果物は、すでに使われ、つまずいた所が直っている」

    場面：受け手が手元でつまずく落とし穴のあるタスクです。たとえば、新しいクローンにはないフォルダを前提にしてしまいやすいセットアップ手順書です。合格は、turn が返した成果物を、turn と関わりのない新しいエージェントが受け手として一度使い、つまずかずに合格の基準に届くことです。

- 「作って、使ってみて、直す流れを、自分のスキルに書かずに済む」

    場面：上の試走を、CCS を書き、`turn:up` を呼び、`next` を読むだけの小さなプラグインから動かします。合格は、そのプラグインのスキルに作る、使う、直すの手順がなくても、上の合格に届くことです。

- 「成果物を読まずに、次の一手を決められる」

    場面：上の試走で返ってきた CCS です。合格は、CCS だけを読んで決めた次の一手が、成果物と会話の記録まで読んで決めた次の一手と同じになることです。

- 「聞かれるのは、利用者にしか決められないことだけ」

    場面：利用者しか知らないこと（たとえば、API トークンを誰が渡すか）を1つ含むタスクです。合格は、それが `gap` に入り、`gap` にほかの問いがなく、利用者の答えを足して呼び直すと、それを使った成果物になることです。

- 「途中で止めても、続きから進む」

    場面：使い手が使い終えたあとで、利用者が止めるよう言うタスクです。合格は、返ってきた CCS と成果物だけを別のクローンに置いて呼び直すと、報告を受け取り終えた所の続きから進み、同じ合格に届くことです。

形が守られているか（CCS の形の確かめ、写しを消すこと、コミットしないこと）は、スクリプトとそのテストで確かめます。機械が決められることは機械に任せると、速く、毎回同じ答えになります。試走の手間は、約束が届いているかに使います。

## 5. 選ばなかったやり方

- 作り手が自分で使ってみて確かめるやり方は選びません。

    作った本人は自分の意図を知っているので、受け手がつまずく所を素通りします。

- 使い手に合格の基準を渡すやり方は選びません。

    基準に沿って使うので、基準が見落としている受け手のつまずきが出てきません。

- 受け取った CCS を書き換えて返すやり方は選びません。

    ターンが途中で切れると、書きかけの CCS しか残らず、やり直す元がなくなります。

- turn が利用者に直接聞くやり方は選びません。

    ターンの外で利用者と何を合意しているかを、turn は知りません。聞くかどうかを turn が決めると、利用者は同じことを何度も聞かれたり、決めたつもりのないことが成果物に入ったりします。
