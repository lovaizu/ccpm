# Product vision of rn

## Roles

- user\
  One who asks rn for a deliverable, such as a document, code or a plugin, for the people it's for.

## Objectives and key results

- O1: the user gets each deliverable they mean, one that the people it's for can use to achieve
  what they're after.
  - KR1.1: the share of the deliverables rn hands over that the people they're for couldn't use
    for what they're after. Lower is better.
  - KR1.2: the time from the user's request to the deliverable, the user's own time answering rn
    included. Shorter is better.

KR1.1 comes first: keep a change that improves a key result only if none before it
gets worse.
Key results have no targets, as a measure made a target stops being a good measure, by Goodhart's
law. They show whether a change brought its objective closer.

## Concept

In everything it does, rn works only on the vital few, the things that decide whether the people a
deliverable is for can use it, and leaves out the trivial many. Joseph Juran named
these two sides of the [Pareto principle](https://en.wikipedia.org/wiki/Pareto_principle): the few
causes that bring most of a result, and the many that bring little.

- The deliverable the user means, drawn out, for O1\
  rn has the user confirm their goal, answer only the questions under it that rn can't settle, and
  sign off the plan and each deliverable before the next work rests on it, and keeps their goal and
  each decision under it as their design tree, so that it draws out the deliverable they mean.
- Every step by best practice, for O1\
  rn plans, makes, and asks the user, each by the best practice of its kind, and lists for the user
  what a best practice settled without asking them, so that each step holds the few things its kind
  of work needs.
- Judged by the people it's for, for O1\
  rn judges each deliverable by whether the people it's for achieve what they're after with it, and
  at each sign-off shows the user what it found those people can do with it, so that it improves
  only what they need.
- Back to the design tree on a problem, for O1\
  rn takes each problem it finds back to the decision in the user's design tree that it comes from,
  so that the user sees each fix as that decision changed.
- The design tree revised on each run, for O1\
  rn revises the user's design tree by what each run found, so that the next run goes toward their
  goal by what rn now knows.
- Best practices improved by each run, for O1\
  rn brings each lesson a run finds to the user as a change to the best practice of its kind, and
  makes the change once they take it, so that every later deliverable of that kind comes better
  from the next run on.
