# ben の設計

ben は、プラグインを目的から出すまで届ける、どのプラグインにも共通のやり方と、プラグインの利用者が README の約束どおりのものを得られるかを確かめる道具を持つプラグインです。この設計書は、ben を作る人、直す人が、ここに書かれた方針から実装を導くためのものです。書かれていない場面に出会ったら、どの方針に当たるかを見て決めます。

## 用語

- 作る人は、プラグインを作り、ben で確かめる人です。

- 約束は、確かめるプラグインの README が、利用者に約束していることです。

- 成果物は、確かめるプラグインが利用者に渡すものです。

- 場面は、確かめの単位です。

    どんな利用者が、どんなリポジトリで、何を頼み、成果物を何に使うかと、約束ごとの合格の項目を持ちます。

- 項目は、利用者に何が起きれば、その約束を得たと言えるかを書いた1文です。

- 指揮者は、`/ben:check` を受けた作る人の会話で、場面を書き、走らせ、結果を残すまでの進め方を判断する役です。

    約束を得たかどうかは判断しません。

- 利用者役は、場面の利用者として確かめるプラグインと話し、成果物を使う AI です。

- 判定役は、項目ごとに、起きたことが項目どおりかを決める AI です。

- 記録は、Claude Code が会話ごと、エージェントごとに残すやりとりの全記録で、JSONL のファイルです。

- 結果は、1回の確かめで残るファイルです。

- 印は、走らせる回数を除く場面の中身すべてから作る文字列で、結果がどの場面のものかを見分けます。

- 形の番号は、結果のうち次の回の ben が読む部分の形に付ける番号です。

- DeepEval は、AI の出力の正しさなどを測る、広く使われている評価の道具です。

- 欠けは、利用者が約束を得られなかった所です。

## 1. 方針

### 合格の基準は、走らせる前に、利用者に起きることで書く

項目は場面と一緒に、走らせる前に書き、出力の形でなく、利用者に起きることで書きます。

走らせてから書くと、見たものに合わせて基準が甘くなります。出力の形で書いた基準は、利用者が約束を得ていなくても通ります。

### 出すかどうかを決めるのは作る人

ben は、起きたことと数値を示すだけで、良くなった、悪くなったとは言いません。

数値だけで決めると、待ち時間が減った代わりに約束を逃した変更を、良いと取り違えます。何を大事にするかは、作る人にしか決められません。

### 足すのは欠けのためだけ、直すのは原因

ben 自身も、どのプラグインも、最小から始め、ben で欠けが見つかった所だけを足します。欠けは、結果の証拠から記録をたどって原因を突き止め、原因を直します。症状を抑える継ぎ足しはしません。

症状ごとに足すと太り、どの部分がどの約束に仕えるかが見えなくなって、直す時に何が壊れるか分からなくなります。症状だけを抑えると、同じ原因が別の所で出ます。どのプラグインもこの順で作ることが、README の「どのプラグインも、同じ順で考え、同じ土台の上に作れる」の中身です。

## 2. 機能

各機能が仕えるのは、[ben/README.md](../../ben/README.md) の「得られること」の項です。

### 場面を一緒に書く

「変更が役に立ったかを、出力の見た目でなく、利用者に起きたことで判断できる」に仕えます。README の「新しいプラグインを確かめる」で、`/ben:check <plugin>` が呼ばれた時に働きます。

作る人には、作る人にしか決められないこと、つまり利用者は誰か、何をしたいか、何が起きればよいか、いま使っている版、場面をどこに置くかだけを聞き、約束は README の言葉のまま写します。GitHub が要る場面では、練習用リポジトリも聞いて場面に書きます。場面は、約束がなければ利用者がはっきり困るものを選びます。ほかの道具でも同じようにこなせる場面では、通っても何も示さないからです。

### 利用者として走らせる

「変更が役に立ったかを、出力の見た目でなく、利用者に起きたことで判断できる」と「まぐれの1回に惑わされない」に仕えます。README の「新しいプラグインを確かめる」と「改善を確かめる」で、場面を承認した後に働きます。

確かめるプラグインを、作る人の Claude Code に設定してあるモデルで、本物のセッションとして走らせ、利用者役が答え、終わったら成果物を使います。turn（AI に何かを作らせるプラグインが使う、同じマーケットプレイスのプラグイン）のように利用者が別のプラグインであるものは、それを呼ぶプラグインを通して走らせます。

公式の `claude plugin eval` は使いません。公式の文書で確かめたとおり、1回の依頼で終わり、プラグインの問い返しに答える利用者役がなく、前の版の結果とも比べられないからです。

同じ場面を何回か走らせ、回によって分かれた項目をそのまま示します。AI のプラグインは、同じ依頼でも回ごとに振る舞いが変わります。1回の合格は、まぐれと見分けられません。

### 判定する

「判定の理由を、その場で確かめられる」に仕えます。README の結果の「証拠」に表れます。

結果に数えた判定は、どれも理由と、記録のどこに何があったかの引用を持ち、その引用は記録のその場所に実際にあります。結果を書く前に機械で照らし合わせ、引用が記録にない判定は数えません。判定役も AI なので、もっともらしい根拠を作ることがあります。確かめていない判定を数えると、作る人はそれを事実として出すかどうかを決めてしまいます。

項目ごとの判定は判定役が、正しさなどの中身の指標は DeepEval が行い、どちらも `claude -p` を通した Claude をモデルに使います。指標を自前で作らないのは、正しさや忠実さが、DeepEval を使うほかの評価と同じ意味を持つようにするためです。

### 測る

「中身と、待ち時間や費用を、同じ1つの結果で見られる」に仕えます。README の結果の「根拠」に表れます。

時間、利用者の待ち時間、答えた回数、読んだ量、トークンは、記録から機械が数え、回ごとと中央値を残します。読んだ量は文字数で数えます。人が読む手間にいちばん近く、モデルを替えても数え方が変わらないからです。

### 結果を残し、前回と比べる

「古い版を走らせ直さずに、変更で何が動いたかが分かる」に仕えます。README の「改善を確かめる」で、`/ben:check <場面ファイル>` が呼ばれた時に働きます。

改善は、同じ場面、同じモデルで残っている前回の結果と比べます。比べられる結果がない時だけ、場面に書いた、いま使っている版を走らせます。モデルが変わった時や、前回の結果の形の番号が違う時も、比べられる結果がない時に当たります。結果が残っていれば、古い版を走らせ直す時間と費用が要りません。どのマシンで確かめても、同じものと比べられます。

### 届け方を示す

「目的から出すまでを、この README だけで進められる」と「どのプラグインも、同じ順で考え、同じ土台の上に作れる」に仕えます。README の「マーケットプレイスを用意する」から「出す」までが、これそのものです。

マーケットプレイスの用意、作り方、確かめ方、出し方のうち、どのリポジトリで作っても効くことだけを、README に置きます。一つのリポジトリでしか効かないことは、そのリポジトリが持ちます。

### 届け方を Claude Code に渡す

「目的から出すまでを、この README だけで進められる」に仕えます。README の「入れる」の後、作る人が Claude Code にプラグインの仕事を頼むたびに働きます。

ben のスキルは、プラグインを作る、直す、出す作業で Claude Code に読まれ、ben の README を読んでそのとおりに進めるよう伝えます。届け方そのものはスキルに写しません。同じ中身の写しが2つあると、Claude Code が README と違うやり方で作業するからです。

## 3. 登場人物と依存

### 届ける時

```mermaid
flowchart TD
  US([利用者])
  B([作る人])
  CC[Claude Code]
  BEN[ben]
  M[(マーケットプレイス)]
  P[プラグイン]
  T[turn]
  W[writ・pith]
  RN[rn]
  G[(GitHub)]
  O[/公式の文書とプラグイン/]
  B -->|目的・承認・マージ・出すかどうか| CC
  BEN -->|届け方と確かめの道具| CC
  O -->|ベストプラクティス| BEN
  CC -->|作り、確かめ、出す| P
  P -->|AI に作らせるタスク| T
  W -->|README と設計書を書いて確かめる| CC
  RN -->|作業の記録と引き継ぎ| CC
  M -->|一覧・テスト・場面・CI| P
  M --- G
  G -->|入れる| US
```

- 利用者は、マーケットプレイスからプラグインを入れて使います。

- 作る人は、目的を決め、README と設計書を承認し、マージし、何を出すかを決めます。

    出すかどうかは、作る人にしか決められません。

- Claude Code は、作る人が決めたとおりに、ben の届け方で作業します。

- ben は、届け方と確かめの道具を持ちます。

    届け方は公式の文書とプラグインをベストプラクティスの源にし、それに従わない所はその理由を持ちます。

- マーケットプレイスは、いくつものプラグインと、その一覧、テスト、場面、CI を持ちます。

- プラグインは、届けるものです。

    フォルダごと利用者に写されるので、利用者に要るものだけを持ちます。

- turn は、AI に何かを作らせるプラグインが、タスク1つを任せる土台です。

- writ と pith は、Claude Code に頼まれて README や設計書などの文書を書き、話し合いを知らない最初の利用者に読ませて確かめます。

- rn は、作る人の作業を記録し、会話をまたいで引き継ぎます。

- GitHub は、issue、プルリクエスト、CI、タグ、Release を持ちます。

### 確かめる時

```mermaid
flowchart TD
  B([作る人])
  C[ben の指揮者]
  S[/場面/]
  P[確かめるプラグイン]
  U[利用者役]
  J[判定役]
  R[/結果/]
  B <-->|作る人だけが決めることを1点ずつ| C
  C -->|書く| S
  S -->|依頼と利用者| P
  P <-->|問いと答え| U
  P -->|記録| J
  U -->|成果物を使った記録| J
  S -->|項目| J
  J -->|判定と引用| C
  C -->|引用を照らし合わせて書く| R
  R -->|次の回の比べる相手| C
```

- 作る人は、利用者は誰か、何が起きればよいか、出すかどうかを決めます。

- ben の指揮者は、作る人と場面を書き、走らせ、判定を照らし合わせて結果を残し、作る人に伝えます。

    良し悪しは決めません。

- 利用者役は、場面の利用者として答え、成果物を使います。

    話し合いも、項目も、プラグインの作り方も知りません。知っていると、項目に沿って使ってしまい、利用者がつまずく所が見えなくなるからです。

- 判定役は、項目ごとに判定し、理由と引用を返します。

    結果のファイルは書きません。

## 4. 作る人のリポジトリに残すもの

場面と結果は、作る人がコミットし、後の確かめ、後の版の ben、人が読みます。形を変える時は、それを読む側が壊れないかを見ます。

### 場面

場面は JSON のファイルで、確かめるプラグイン、いま使っている版、確かめる時のリポジトリと事前の準備、依頼、利用者がどんな人で何をしたいか、成果物を何に使うか、正しい成果物が持つ事実があればそれ、GitHub が要る時は練習用リポジトリ、走らせる回数、約束ごとの項目を持ちます。

- 約束の言葉は、README のまま写します。

    README が言い換えられた時に、どの約束を確かめた結果かが分かるためです。

- 場面のどこかを変えると、新しい場面になり、前の結果とは比べません。

    どこを変えても、利用者に起きることが変わりうるからです。場面の欄の名前を変える時も、印が変わって前の結果と比べなくなります。走らせる回数だけは、利用者に起きることを変えないので、変えても同じ場面です。結果は、印でどの場面のものかを見分けます。

### 結果

結果は、場面ごとのフォルダに、確かめた版と日時を名前にした md のファイルとして残します。どのプラグインでも同じ形で、人がそのまま読み、次の回の ben がそこから読み取って比べます。機械向けの写しを別に持たないのは、同じ中身の写しが2つあると食い違い、作る人が読む結論と ben が比べた値が違ってしまうからです。形は人でなく機械が書くので崩れません。

- 先頭に、プラグイン、版、コミット、日時、場面とその印、使ったモデル、回数、比べた相手、形の番号を持ちます。

    次の回は、同じ場面の印と同じモデルの結果だけを比べる相手にします。

- 本文は、結論、根拠、証拠の順です。

    結論は約束ごとに「何回中何回得られた」と前回の値、根拠は回ごとの判定と理由・指標・数値、証拠は記録の場所と引用です。作る人は結論から読み、必要な所だけ下ります。

- 次の回の ben が読むのは、先頭、結論、根拠の数値です。

    結論、根拠、証拠は、`## 結論`、`## 根拠`、`## 証拠` の見出しで分けます。証拠は人が読むためのもので、形を自由に変えられます。

- ben が読む部分の形は、番号を持ちます。

    項目の名前や意味、数値の書き方を変える時は形の番号を上げ、前の番号の結果は比べる相手にしません。読めない形を読み違えて比べるより、比べないほうがよいからです。項目を足すだけなら、前の版の ben も知らない項目を読み飛ばせるので、番号は上げません。

## 5. ben 自身の確かめ方

ben は ben で確かめます。題材は、同じマーケットプレイスの writ のように、利用者が人で、約束がはっきりしたプラグインです。作る人役は、話し合いを知らず、結果を読んで出すかどうかを決める AI です。記録を全部読んだ人は、その変更で利用者に何が起きたかを記録から確かめた、ben を作る人です。

約束ごとの合格は、次のことが起きることです。

- 目的から出すまでを、この README だけで進められる：ben だけを入れ、作り方の決まりのファイルがないリポジトリで、作る人役が目的を伝えると、Claude Code が README の順でプラグインを作り、確かめ、出すまで進むこと。

- どのプラグインも、同じ順で考え、同じ土台の上に作れる：違う目的のプラグインを2つ頼んでも、どちらも README、設計書、実装、確かめの順で進み、同じ置き方になること。

- 変更が役に立ったかを、出力の見た目でなく、利用者に起きたことで判断できる：利用者が約束を逃すとはっきり分かっている変更と、逃しを直した変更を、作る人役が結果だけを読んで判断し、記録を全部読んだ人と同じ判断になること。

- まぐれの1回に惑わされない：3回に1回ほどしか約束を守らない変更で、作る人役が結果だけを読んで、まだ出せないと判断すること。

- 判定の理由を、その場で確かめられる：作る人役が、結果の引用から記録のその場所をたどれること。

- 中身と、待ち時間や費用を、同じ1つの結果で見られる：待ち時間が減った代わりに約束を逃した変更を、作る人役が結果だけを読んで見抜くこと。

- 古い版を走らせ直さずに、変更で何が動いたかが分かる：改善を確かめる時に、古い版が走らず、前回の結果と並べた結論が出ること。

場面は、見た目では良くなるのに利用者は困る変更にします。テストが通り、出力が整っているのに利用者がつまずく変更でこそ、ben がないと作る人が見逃すからです。

確かめの手間は、上の約束にかけます。引用の照らし合わせや結果の読み書き、比べる相手の選び方のように、機械で決まることは、ben のテストが受け持ちます。
