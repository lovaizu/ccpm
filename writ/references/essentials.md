# 本質的な観点

書く人は書く前に上から読み、確かめる人は問いを1つずつ文書に当てて、届いているかを決める。

## すべての文書

決めた読み手が、上から読み進めるだけで全体が分かり、読んだあとにすべきことができるか。

- 読み手が1人に決まっているか。

    誰が読むか、読んだあと何を決め何をするか、どう読むか（通して読むか、必要なところを引くか）を、書く前にそれぞれ1行で言える。声、順序、図、締め方は、この3つから決める。読み手が2人いる中身は、読み手ごとの文書に分ける。

- 読み手に要るものがそろい、どの文もその核か。

    網羅でなく核に絞る。核が多いのは、まだ磨ききれていない印。読み返す人、過去のレビュー役、承認する人のような、別の人のための文は、その人の文書へ移す。読み手に要るのに置き場所のないものは、置き場所を足す。冒頭の1文から核を言う。

- 上から読み進めるだけで、行き来せずに分かるか。

    結論やベネフィットを先に置き、具体的な流れ（例）を抽象的な型より先に見せる。言葉は、初めて出るところかその前で中身が分かる。理由は、決めたことのその場に1文で書く。

- 見出しだけを上から読んで、筋が通るか。

    見出しは、その節の核の主張か、読み手がそこで抱く問い。見出しは、型からでなく、読み手の問いの順に組み立てる。

- どのことも一度だけ言っているか。

    題名、図、ほかの文から読み取れることは書かない。方針、いつも成り立つ条件、代償、選ばなかったやり方、仮定は、それぞれ決めたことのその場に置く。

- 今の姿だけを持っているか。

    書くのは、今決まっている姿。決めてきた経緯と変更の履歴は、コミットメッセージと PR に置く。

- 構造と流れが、一目で見えるか。

    登場人物とそのやりとり、順序、分岐、状態の移り変わりは図にする。文書やファイルも1つずつ登場人物として描き、誰が書き、誰が読み、どこへ移るかを描く。図は局所ごとに分け、縦向きにし、ラベルを短くする。各節は図を先に置き、文は図にないことだけを言う。表は、いくつかのものを同じ欄で比べるところに使う。

- 並んだ項目が、説明を読まずに見渡せるか。

    項目は、それだけで意味の通る1文にし、太字にしない。説明は、空行のあと字下げして下に置く。太字は、読み落とすと判断を誤るところだけに使い、要の主張が一目で分かるようにする。

- 1つのものに、1つのふつうの言葉を当てているか。

    同じ言葉は1つの意味で使う。言葉は、専門用語や造語より、ふつうの言葉を選ぶ。役割は、していることが分かる名前で呼ぶ。物は、使う人に見える名前で呼ぶ。

- 言っていることの確かさが、読み取れるか。

    確かめた事実は言い切り、確かめていないことは仮定と書き、決めたことは決めたことと書く。元の下書きにある提案や仮説は、その印のまま運ぶ。言い切れないところは、根拠か「未確認」を書く。うまくいかない点、代償、限界も書く。

- 読み手に合った1つの声で、人が書いたように読めるか。

    声と調子は読み手から決める。AI の書いた跡（埋め草、言い直し、一般論への逃げ、味のないつなぎ、反射的な箇条書き、揺れる声、緩衝表現）は、最後に取り除く。

- 題材そのものの欠陥が、見えるまま残っているか。

    読み手がつまずく原因が書き方でなく題材（決まりの穴、主張どうしの食い違い）にあるときは、題材の欠陥として名指しし、持ち主に返す。

## README

読み手は、その製品を初めて知った使う人。読んだあと、自分に何をしてくれるかが分かり、使うかを決め、使い始められる。

- 冒頭で、何が楽になり、何が起きなくなるかが分かるか。

- 完成した製品を使う体験として書かれているか。

- 始めてから結果を得るまでの段と、各段で何をし何を得るかが、一目で分かるか。

- 例は、読み手が自分の仕事として思い浮かべられる場面か。

    製品の強みが見え、読み手自身の仕事に近い場面を選ぶ（例: JavaScript のアプリを TypeScript に移す）。よその製品の名前やその作り直しは使わない。

- 使う人に見えるものだけで書かれているか。

    内部の役割名と、新しく使う人に要らない例外は、設計書に置く。なぜこの形にしたかは、設計書へのリンクに任せる。

- 手に入れて使い始めるまでの手順と、使ってよい条件（ライセンス）があるか。

## 設計書

読み手は、作る人と直す人（人と AI）。読んだあと、README の姿がどう実現されるかが分かり、ある変更が設計に合うか、合わないならなぜかを言える。

- どう作るかの方針が数個に絞られ、それぞれ言い切られているか。

    1文の主張のすぐあとに、外すと何が起きるかを書き、README の姿か、設計では変えられない条件（使う環境、使う人）までつなげる。1つの機能だけの決まりは、その機能のところに置く。

- 直す人が問う順に、骨組みがあるか。

    役目と境目（誰が何をし、何を決めるか）、状態と操作（どんな状態があり、操作でどう動くか）、判断の基準（何を見てどちらに分けるか）、残るもの（何が残り、誰が書き、誰が読むか）。

- どの操作のあとも成り立つべき条件が、それと分かる形で書かれているか。

- 決めたことに、何を諦めたかと、ほかのやり方を取らない理由が添えられているか。

- README からも実装からも読み取れない、意図と決めたことだけが書かれているか。

    コードの分け方、ファイル名や関数名、内部のデータの形、処理の手順は、実装とテストに置く。書き足す前に、「README か実装を読めば分かるか」「実装を変えたらこの文も変わるか」を問い、どちらかが yes なら実装に任せる。名前は、使う人に見える名前と、外との取り決め（保存する形、渡す形）で書く。

## ルール・観点・指示の文書

読み手は、その文書に沿って動く人か AI。読んだあと、その場ですべきことができる。

- するべきことが、肯定の形で書かれているか。

    書くのは、するべきことだけ。無いものの説明、そう決めた経緯や理由、そのときの作業だけの決まりは、コミットメッセージと PR に置く。
