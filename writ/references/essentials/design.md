# Design doc

The readers are builders and maintainers, who may be people or AI. When they finish, they know which features give the user the README's benefits and how each is built, and can explain whether a given change fits the design and, if not, why.

- Can a builder decide which way to go when unsure, by remembering just a few policies?

    State each policy flatly in one sentence, and right after it write what happens if it is not kept. Trace that explanation until it reaches a benefit in the README, or a condition the design cannot change, such as the environment the product is used in or the user. Write a rule that concerns only one feature where that feature is described.

- Can a maintainer follow each benefit in the README to the features that give it and the section that builds each, and so get a sense of where to fix?

    A feature is what the product provides toward one of the README's benefits, such as a checker that did not make the work checking it, with the fixes settled before the user is called. First list the features, each naming the benefit it serves and the step of use in the README where it works; every benefit has at least one. Then give one section per feature, named after the feature, saying how it is built: the roles and their boundaries, who does what and who decides what; the states there are and how operations change them; the criteria for judgment, what is looked at and which way things are sorted; and what remains, who writes it and who reads it. Last come the qualities. Every feature, section, role, state and handoff traces back to a benefit; one that traces to nothing is either not needed or points to a benefit or feature that is missing. Features listed without the benefit each serves, or sections named after mechanisms, leave the maintainer unable to tell what a change costs the user; one benefit sentence followed straight by the mechanism skips the features, so no one can tell which part gives which benefit.

- Can a maintainer tell which conditions must hold after every operation?

    Write each such condition at the decision it concerns, phrased so it reads as a condition that always holds, as in "after every operation, ...".

- Can a builder decide, for each quality the goal calls for checking, how to check it, what passes, and how far to check?

    Check only whether the user gets the benefits. Draw the qualities one by one from the README's benefits, and for each quality write which benefit it is for and what the user struggles with if it is missing. Write the pass criteria as what happens to the reader or the user. Whether a feature works as designed is a clue for finding the cause when the user does not get a benefit; it is not a quality. When qualities are drawn from the design's own list of features, someone checks that the features work, but no one checks whether the user gets the benefits. Also write what you gave up when deciding how far to check. Without a written way to test, the way of checking varies by builder and by change. Without written pass criteria, even after the tests run, no one can decide whether it can be said to be realized.

- Can a builder secure the benefits before what the user takes for granted, and check each benefit itself?

    The benefits are what the product gives beyond what the user would use instead, such as another tool or doing the work by hand; what that also gives, the user takes for granted, such as nothing being lost. Write the benefits first, each with its check, and then what the user takes for granted. Build in the same order: move on to what the user takes for granted only once the benefits pass. Judge each trial run first on the benefits, and while they fail, do not fix first what the user takes for granted. Failures of what the user takes for granted are the easiest to see, so fixing whatever a run shows first fixes only those, and run after run the benefits are never measured. A product that is only correct gives the user no reason to choose it. Checks of what the user takes for granted are easier to write, so they multiply and crowd out the checks that show why the user would choose the product; then every check passes while no one has checked whether the user would choose it. A check of a benefit measures it as the user would feel it, not that an artifact has the form meant to bring it. For example, if the user should be able to approve from a summary without rereading the work, the check is whether a user who reads only the summary makes the decision they would make after reading the work, not whether the summary lists each point with where it is. Run the check on a case where, without the benefit, the user would visibly lose out, such as first words from the user that would build the wrong thing if taken as they are; on first words that were already right, a check that a rough goal is enough passes without testing anything. A check of form reads like what happens to the user, so it slips past, and it passes even when the user does not get the benefit.

    Leave to tests or scripts the checks of what the user takes for granted that a script can decide, such as a format holding, nothing being lost or a link resolving. They are faster and give the same answer every time, and an AI checker that spends its attention on them has less left for the judgment only it can make: whether the user gets the benefit. What the user takes for granted but no script can decide, such as whether a claim is true, stays with the AI checker.

- When a maintainer wants to switch to another option, can they see what switching would lose and why it was not chosen?

- Does the reader get here the intent and decisions they cannot read from the README or from the implementation?

    Every sentence says something that reading the README or the implementation does not reveal, and that does not change when the implementation is rebuilt. Take each part away and ask whether a maintainer would then judge some change differently, or be unable to judge it; if not, it does not belong. Name the benefit a feature serves, but do not restate the README's benefits or its flow of use; a restatement drifts from the README each time either changes. So write decisions as intent and conditions that always hold, not as the settings or procedures that realize them. The same goes when there is no implementation yet: settings or procedures make the design doc go stale each time the implementation is rebuilt. How the code is split, file and function names, internal data structures and processing procedures do not belong in a design doc. Mention by name only what people who use it can see, and external agreements. External agreements are the formats of what remains in the user's environment and of what later versions read; handoffs between roles are not included. Later versions and people both read external agreements, so write why each item exists and the conditions that always hold, and show the form with a real filled-in example. Give the form one home, the design doc, because it survives rebuilding the implementation; the implementation points there instead of carrying a copy, since two copies drift apart. Show the directory layout as a full tree only for what remains in the user's environment and what later versions read, and mark where the user may and may not make changes.
