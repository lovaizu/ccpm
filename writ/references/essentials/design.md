# 設計書

読み手は、作る人と直す人で、人も AI もいる。読み終えたら、README の姿がどう実現されるかが分かり、ある変更が設計に合うか、合わないならなぜかを言える。

- どう作るかの方針が数個に絞られ、それぞれ言い切られているか。

    1文の主張のすぐあとに、守らないと何が起きるかを書き、README の姿か、使う環境や使う人のような設計では変えられない条件までつなげる。1つの機能だけの決まりは、その機能のところに置く。

- 直す人が知りたい順に、骨組みが書かれているか。

    誰が何をして、何を決めるかという役目と境目。どんな状態があり、操作でどう動くか。何を見てどちらに分けるかという判断の基準。何が残り、誰が書き、誰が読むか。

- どの操作のあとも成り立つべき条件が、それと分かる形で書かれているか。

    その条件に関わる決めたことのところで、「どの操作のあとも〜」と、条件だと分かる言い方で書く。

- 決めたことに、何を諦めたかと、ほかのやり方を取らない理由が添えられているか。

- README からも実装からも読み取れない、意図と決めたことだけが書かれているか。

    どの文も、README や実装を読んでも分からず、実装を作り直しても変わらないことを書いている。コードの分け方、ファイル名や関数名、内部のデータの形、処理の手順は、設計書の核ではない。名前は、使う人に見える名前と、保存する形や渡す形のような外との取り決めで書く。
