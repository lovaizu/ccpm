# プロンプト

読み手は、そのプロンプトに従って動く AI。読み終えたとき、書き手が想定していなかった場面でも、目的を果たせる動き方を自分で選べる。

- 目的、役割、手順の3つで組み立てられているか。

    目的には、なぜそれが必要かを添える。理由を知っていれば、書かれていない場面でも目的に合うほうを選べる。役割には、誰として読み、何を自分で決め、何を決めずに依頼元へ返すかを書く。

- 手順には、その場に固有の決まりだけが書かれているか。

    手順に書くのは、受け渡しの形式のように、ずれると壊れるうえに目的と役割からは導けない決まりだけにする。手順は書かれたとおりに守られるので、想定と違う場面では的を外す。目的と役割で足りるところは読み手に任せる。各段階で使う決まりは、その段階に書く。別の文書を読ませる箇所には、パスと読む理由だけを書き、要約は添えない。

- 作る役と確かめる役が分かれているか。

    作る役と確かめる役は、同じ観点を読む。作る役は観点を目指す姿として読み、確かめる役は問いとして読む。確かめる役には、作る役がそうした理由を渡さない。どちらの役も観点ごとに Good と More で答え、依頼元に返す。Good は、目的に役立っていて、直すときに壊してはいけないところ。More は、足りないところと、それによって読み手が何に困るか、どう直すか。どちらにも、path:line や実行したコマンドとその出力のような根拠を添える。

- 次に何をするかを決めるのは、依頼元だけか。

    確かめる役は、直すかどうかも、次に何をするかも決めない。確かめた結果を字面どおりに受けて動くと、目的に役立っている部分までやり直すことになる。依頼元は、返ってきた More を1つずつ目的に照らし、直すか、見送るか、人に渡すかを決める。

- 観点は、本質的なものだけに絞られているか。

    観点は禁止事項の一覧にせず、同じ原因から生じる誤りをまとめて捉える問いにする。また、手順を踏んだかどうかでなく、できあがったものの状態で確かめられるように書く。本質的でない観点が混ざると、作る役の狙いがずれ、読む量が増え、直しても終わらないか、人の負担が増える。確かめる役の答えが浅いなら、観点が多すぎるか、ぼやけているかのどちらかなので、役を増やさず観点を磨く。

- 観点は、作るものごとに1か所にまとまっているか。

    ほかの文書には、観点のファイルがあることと、誰がどう使うかだけを書き、内容は写さない。写すと、観点を磨くたびに内容がずれていく。

- すべきことが、肯定の形で書かれているか。

    存在しないものの説明、決まるまでの経緯、そのときの作業にしか関わらない決まりは、すべきことではない。
