# プロンプト

読み手は、そのプロンプトに沿って動く AI。読み終えたら、書いた人が思い描いていなかった場面でも、目的を果たす動き方を自分で選べる。

- 目的、役割、手順の3つで組み立てられているか。

    目的には、なぜそれが要るかを添える。なぜを知っている読み手は、字面の外の場面でも目的に合うほうを選べる。役割は、誰として読み、何を自分で決め、何を決めずに返すか。

- 手順には、その場に固有の決まりだけがあるか。

    手順に書くのは、ずれると壊れる受け渡しの形のような、目的と役割から読み手が導けない決まり。手順は字面どおりに守られ、場面が想定と違うと的を外すので、目的と役割で足りるところは読み手に任せる。各段で使う決まりは、その段に置く。別の文書を読ませるところには、パスと読む理由だけを置き、要約を添えない。

- 作る役と確かめる役が分かれているか。

    作る役と確かめる役は、同じ観点を読む。作る役は観点を狙いとして読み、確かめる役は問いとして読む。確かめる役には、作った役の理由を渡さない。どちらの役も、観点ごとに Good と More で答えて、頼んだ役に返す。Good は狙いに役立っていて、直すときに壊してはいけないところ。More は足りないところと、そのせいで読む人に何がまずいか、どう直すか。どちらにも、path:line や実行したコマンドと出力のような根拠を添える。

- 次の一手を決めるのは、頼んだ役だけか。

    確かめる役は、直すかどうかも次に何をするかも決めない。確かめた結果の字面どおりに動くと、目的に役立っている作業までやり直すことになる。頼んだ役は、戻ってきた More を1つずつ目的に照らし、直すか、見送るか、人に渡すかを決める。

- 観点は、本質的なものだけに絞られているか。

    観点は、禁止事項の一覧でなく、同じ原因から出るまちがいをまとめてとらえる問いにし、手順を踏んだことでなく実物の状態で確かめられるように書く。本質的でない観点が混ざると、作る役がずれ、読む量がふくらみ、直しが収まらないか、人の負担が増える。確かめる役の答えが浅いなら、観点が多すぎるか鈍すぎるしるしなので、役を増やさず観点を磨く。

- 観点は、作るものごとに1か所にだけあるか。

    ほかの文書には、観点のファイルがあることと、誰がどう使うかだけを書き、中身を写さない。写すと、観点を磨くたびにずれる。

- するべきことが、肯定の形で書かれているか。

    無いものの説明、決めてきた経緯、そのときの作業だけの決まりは、するべきことではない。
