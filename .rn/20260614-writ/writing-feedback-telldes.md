# 文書のノウハウと観点（Telldes からの FB）

> このセッションの素材（source of record）。Telldes のセッション（figma-plugins-6f）が、`.rn/doc-review.md`（README と設計書の観点）とユーザーから受けた文書へのフィードバックを、製品に依らない形にして送ってきたもの。受け取ったまま載せる。

文書作成のスキルを writ に集めるため、Telldes のセッション（figma-plugins-6f）で使っている文書のノウハウと観点を送ります。writ のスキルに取り込んでください。

出どころは Telldes の `.rn/doc-review.md`（README と設計書の観点）と、ユーザーから受けた文書へのフィードバックです。製品に依らない形にしてあります。

■ 1. README と設計書の観点（`.rn/doc-review.md` の全文。README か設計書を書く人とレビューする人が使う。書く人は書く前に上から読む。レビューする人は、観点を1つずつ文書に当てて OK か NG かを決める）

## 2つの文書の役目
README と設計書には、製品の目指す姿を書く。目指す姿とは、実装がそろったときに製品がそうなっているべき姿のこと。実装はこの2つをゴールにして作り、2つの文書は実装に合わせて書き換えない。変えるべきことが見つかったら文書を先に変え、実装を従わせる。文書の変更は作業のブランチで先に入れ、実装と一緒に main に入れる。main の README は、いつも今使える姿になる。

- README: 読む人＝製品を初めて知ったユーザー／伝えること＝ベネフィットと使い方／読んだあとにできること＝自分に何をしてくれるかが分かり、使うかを決め、使い始められる
- 設計書: 読む人＝作る人・直す人（人と AI）／伝えること＝README の姿をどう実現するか／読んだあとにできること＝実現の仕方が分かり、ある変更が設計に合うか、合わないならなぜかを言える

使い方の詳しい手順は別のファイルに分けて、README からリンクしてよい。そのファイルには README の観点2〜6と共通の観点を当てる。

## 書くこと、書かないこと
書くのは、目指す姿と、それを支える理由・代償・仮定。README と設計書を満たしていれば実装が自由に選んでよいこと（コードの分け方、関数やファイルの名前、内部のデータの形）は書かない。使う人に見えるもの（入れるもの、動く環境、画面の言葉）は、実装の中のものでも書いてよい。
見出しは、読む人が読みながら抱く問いの順に、その問いか答えを置いて組み立てる。

## 共通の観点（観点／OK の姿／NG の印）
A 実装が自由に選ぶことが無い／実装を作り直しても書き換えずに済む／コードの分け方、コードのファイル名や関数名、内部のデータの形が出てくる
B 見出しで筋が追える／見出しだけを読んで、問いか主張の流れが分かる／「概要」「その他」のような見出し
C 表は比べるときだけ／表は、いくつかのものを同じ欄で並べて比べるところだけにある／筋道が表のセルに切り刻まれている
D 経緯を書かない／今の姿だけが書いてある／「以前は」「〜に変えた」のような、時間を追った話がある
E 項目の並びが見渡せる／説明を伴う項目は、項目を1行で言い切り、説明は改行して下に置いてある。項目の1行は、説明を読まなくてもそれだけで意味が分かる／項目の主張と説明が1つの文の並びに混ざり、何が並んでいるかが読まないと分からない。項目の1行が「それ」「気にするもの」のように、説明を読まないと中身が分からない

## README の観点
1 ベネフィットが先／冒頭で、何が楽になり、何が起きなくなるかが分かる／冒頭が機能の並びや作りの説明で始まる
2 目指す姿で書く／完成したものを使う体験として書いてある／使い方に「今は」「まだ」「予定」がある
3 流れが一目で分かる／始めてから結果を得るまでの段と、各段で何をし何を得るかが見える／細かい手順が並び、全体の流れが埋もれている
4 理由は設計書に任せる／なぜこの形にしたかは、設計書へのリンクで済ませている／なぜこの形にしたかの説明がある
5 前知識なしで読める／言葉が、初めて出たところで分かる／読む人がまだ知らない言葉が、説明なしに出てくる
6 使い始められる／手に入れて使い始めるまでの手順と、使ってよい条件（License）がある／手順が途中で終わっている。License が無い

## 設計書の観点
1 位置づけを言い切る／冒頭で、README の姿を実現する方法の文書であり、実装と食い違ったらこちらが正しいと言っている／冒頭が概要や目次の繰り返し
2 方針を言い切る／どう作るかの方針が数個あり、それぞれ1文の主張のすぐ後に、外すと何が起きるかが続き、README の姿か、設計では変えられない条件（使う環境、使う人など）までつながる／理由が別の箇条に切り離されている。1つの機能だけの決まりが方針に混じる
3 骨組みがある／直す人が問う順に、役目と境目（誰が何をし、何を決めるか）、状態と操作（どんな状態があり、操作でどう動くか）、判断の基準（何を見てどちらに分けるか）、残るもの（何が残り、誰が書き、誰が読むか）がある／方針だけで、誰が何をするかが分からない。判断が、場合ごとの結論の一覧になっている
4 いつも成り立つ条件を名指しする／どの操作のあとも成り立っていなければならない条件が、それと分かる形で書いてある／その条件が文の途中に埋もれ、どれを守ればよいか分からない
5 代償と、選ばなかったやり方がある／何を諦めたか、ほかのやり方をなぜ取らないかが、今の比べ方として分かる／選んだものの良い点だけが書いてある
6 名前は外から見えるものだけ／使う人に見える名前と、外との取り決め（保存する形、渡す形）だけで書いてある／コードのファイル名や関数名が出てくる
7 事実・仮定・決定を分ける／確かめた事実は言い切り、確かめていない事実は仮定と書き、決めたことは決めたこととして書いてある／確かめていないことや決めたことが、確かめた事実のように書いてある

## 指摘の分け方（種類／どういうときか／例／扱い）
- 書き方／文書の中で直せる／分かりにくい文、同じことの繰り返し／書いた人が直す
- 置き場所／よその文書へ移すか消せば直る／README に設計の理由がある。どちらの文書にも書かないこと（コードのファイル名）がある／役目の合う文書へ移す。どちらにも合わなければ消す
- 中身／決まりそのものを変えないと直らない／決まりに穴がある、2つの主張が食い違う／文章でごまかさず、製品の持ち主に出す

## レビューを頼む人へ
文書ごとに、書いた経緯を知らないレビュー役を1人立てる。渡すのは、その文書と、上の「2つの文書の役目」「書くこと、書かないこと」「共通の観点」、その文書の観点、「指摘の分け方」だけにする。
レビュー役には、その文書の読む人として上から読ませ、次を報告させる。
- 読んだあとにできることができたか
- 見出しだけで筋が追えるか
- どこでつまずいたか
- 要らなかったものは何か、それは誰のためのものか
- 観点ごとの OK / NG と、NG ならその箇所
- 指摘ごとの種類（書き方・置き場所・中身）

■ 2. 書き方のノウハウ（ユーザーのフィードバックから）

- 見出しの型（テンプレ）を持たない。役目と観点から見出しを組み立てる。
  理由: 枠を埋めるように書くと、要らない中身まで入る。

- 設計書には、README や実装からは読み取れない意図と決めたこと（とその理由・代償）だけを要点で書く。
  細かいロジック（変換・計算・判定・API・データの項目）は実装とテストに置き、使い方は README に置く。処理の手順や出力の中身の一覧のように、実装を見れば分かるものは書かない。書き足す前に「README か実装を読めば分かるか」「実装を変えたらこの文も変わるか」を問い、どちらかが yes なら書かない。
  理由: 書き足し続けた結果、1459行の読めない設計書になった。

- 図と文で同じことを言わない。

- 経緯や変更履歴は書かず、最新の意図と決定だけを今の形で書く。

- 太字は、読み落とすと判断を誤るところだけに使う。
  各箇条の先頭を毎回太字にしない。どこも太字だと、どこも目立たない。

- 言葉とラベルは、初めて出る場所かそれより前で中身を書く。
  「（3.1 参照）」のように後ろの節へ意味を預けない。記号的なラベル（「原則A」など）は、中身を言う普通の言葉に置き換えられないかを先に考える。書き終えたら上から読み、初めて出る言葉が説明済みかを確かめる。

- ルール・観点・指示の文書には、するべきことを肯定の形で書く。
  無いものの説明（「〜は持たない」）、そう決めた経緯や理由、そのときの作業だけの決まり（「レビューは1回」など）は書かない。書き終えたら「〜しない」「〜は無い」「〜だから」の文を探し、するべきことに言い換えるか消す。

- ふつうの言葉で書く。専門用語や造語は避ける。

- 物事は、使う人に見える名前（ボタンの名前など）で呼ぶ。

- レビューの指摘は、文書の目的に効くものだけ直す。
  言い回し・好み・起きそうにない場合への備えは直しに回さず、理由を一言添えて見送る。指摘をすべて直すと、直しのラウンドが膨らむ。

- 文書を正とする。
  README → 設計書 → 実装の順に依存し、変えるべきことが出たら文書を先に変える。

- 書いた文書は、上の「レビューを頼む人へ」の回し方でレビューを1回回して直し、結果をユーザーに見せる。
