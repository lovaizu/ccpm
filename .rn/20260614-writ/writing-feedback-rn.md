# 文書の書き方のノウハウ（rn 再構築からの FB）

> このセッションの素材（source of record）。rn（ccpm PR #33）の README と設計書を直す中でユーザーと合意し、rn の本質的な観点から外して writ に移したもの。受け取ったまま載せる。

writ（文書作成スキル）に集める、文書の書き方のノウハウです。rn（ccpm PR #33）の README と設計書を直す中で、ユーザーと合意しました。rn の本質的な観点からは外し、writ に移します。

■ 文書の本質的な観点（1つの問い）
文書はどれも、上から読み進めるだけで全体が分かり、どの文も読む人に要る核で、題名や図やほかの文から読み取れることを繰り返さず、今の状態だけを持つ。
（「冒頭の説明を書かない」のような禁止事項を足さず、この問いで同じ根から出るノイズをまとめて捉える。禁止事項の一覧は、載っていない形のノイズを防げないため。）

■ この問いを具体にしたノウハウ
1. 網羅を目的にしない。核に絞る。核が大量にあるなら、まだ洗練されていない。
2. 上から読み進めるだけで、認知負荷なく全体が分かる順にする。抽象的な共通の型より先に、具体的な流れ（例）を見せる。
3. 見出しだけを上から読んで筋が通るようにする。見出しは、その節の核の主張にする。
4. 各節は図を先に置き、説明は図にないことだけを書く。図と説明を重複させない。
5. 番号やリンクで別の節を参照させない。読む人は行き来したくないし、書く側も保守が大変になる。理由は、決めたことのその場に1文で書く。
6. 方針・不変条件・代償・選ばなかったやり方・仮説の一覧のように、同じことを別の角度から繰り返す節を作らない。決めてきた経緯はコミットメッセージ（と PR）に残し、文書は今の状態だけを持つ。
7. 冒頭の「この文書は〜を説明する」のような、題名や中身から読み取れる前置きを書かない。
8. 登場人物とその間のやりとりは、図で示す。文書やファイルも登場人物として1つずつ描き、「記録」のような1つの箱にまとめない。誰が書き、誰が読み、どこへ移るかを描く。1枚に詰めず、局所化して図を分ける。
9. 図は縦向きにする（横向きは PR 上で小さくて読めない）。ラベルは短くする。
10. 用語は、1つのものに1つの言葉を当てる。同じ言葉を2つの意味で使わない。定義のない造語（例: maker）を足さない。役割の名前は、していることがそのまま分かる名前にする（例: generator / evaluator）。
11. 箇条書きの形:
    - 項目は太字にしない。
    - 項目は、それだけで意味が通る1文にする。
    - 説明は、空行のあと字下げして下に書く。説明が要らない短い項目は、1文だけでよい。
    - 手本: https://github.com/lovaizu/telldes/blob/telldes-plugin/README.md の「どう使うか」
12. README の例は、読む人（例: Claude Code を使うエンジニア）が自分の仕事として思い浮かべられるものにする。製品の強みが見える場面を選ぶ（例: JavaScript のアプリを TypeScript に移す）。クローンや、他社の名前は使わない。
13. 使う人向けの文書（README）には、内部の役割名や、新しく使う人に要らない例外を出さない。
