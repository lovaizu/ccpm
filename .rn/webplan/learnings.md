# learnings — 仮案件の手動実走から得た学び

#1 の実走中に、ユーザー FB から抽出した観点を先に積む（走りながら追記）。#1 の最後に worklog を一般化して
〔決定の一覧と順序／各決定の入力と出力／v1 に足りなかったもの／v1 から引き継ぐもの〕を足す。
社名・実額・個人名・他社著作物の複製は書かない。

## 起案の観点（AI が起案を出す前に自分で当てる）

計画の起案は、出す前にこの観点で自己検査する。同じ FB を二度受けない。

### 構造

1. **正は計画、提案書・見積はビュー。** 最終成果物を提案書と置かない。計画は開始後もメンテし、ビューは更新しない。
2. **アウトラインで考える。** 「前提／決定／定数／履歴」のような抽象分類でなく、読者が何を知りたいかから見出しを引く。
3. **見出しは英語・単数・曖昧語なし。** Overview のような何でも入る語は使わず、Goal のように中身が一語で分かる語にする。
4. **見せ方は計画に持ち込まない。** AsIs/ToBe を並べるのはビューの都合。計画では分ける。
5. **一つの見出しに二つのものを同居させない。** 「どの案か」と「何を守るか」は別（Scope と Priority）。
6. **与件と決定を分ける。** Team（誰が居て何ができるか）は決定でなく事実＝Context。決めるのは Planning だけ。
7. **依存がストーリーとして繋がるか、起案のたびに辿る。** 各見出しは上流だけを根拠にし、Contract・ChangeLog 以外は下流に使われる。
   切れ（根拠の無い決定・使われない決定）を出す前に見つける。

### 文

8. **本文は Client にそのまま出せる文で書く。** 提案書は計画のビューなので、計画の文がそのまま外へ出る。
   原文引用や「〜と感じている」の報告調でなく、理解して言い直す。根拠行はトレース用、Provider 限定のメモは「Provider note」に分ける。
9. **役割名は Client／Provider で統一する。** 施主／提案者と混ぜない。
10. **固有物は名前で呼び、必要ならリンクにする。** 生の URL・パス・ID を本文に出さない（サイトはサイト名）。対象ページを示すときはページタイトルをラベルにしたリンクにして、すぐ開けるようにする（計画でも提案書でも同じ）。
11. **気の利いた表現にしない。** 短く、事実と提案だけ。

### 判断

12. **聞く前に提案する。** Client に決めてもらう項目も「未聴取」で投げず、Provider の案を出して確認を求める。合意を求める書き方（「合意する」）でなく提案の書き方にする。
13. **指標は目的に直結するものだけ。** 目的がキャリア採用なら、採用に効かない指標（見た目の評価）は成功の定義に入れない。
14. **1 問ずつ、変更点だけ提示する。** OK が出た部分は再掲しない。
15. **人の判断は「最終成果物のアウトライン」と「提案の方針」だけ。** 見出しごとの文言確認を求めない。方針が決まったら AI が全見出しを一気に起案し、
    ストーリーの整合（上流→下流の根拠、Client の目的達成と Provider の対価の両立）を自分で検査してから全体を提示する。
16. **契約形態を先に置く。** 準委任か請負かで Team・Process・Cost の書き方（引き渡し／稼働、完成責任、再委託）が変わる。方針の段階で決める。
17. **自明なことは書かない。** 「契約と窓口は Provider が一本」のように相手が当然知っていることは本文に出さない。
18. **提案の大きさは Client の依頼に合わせる。** 「見た目を直したい」に段階分けや新企画を足さない。Provider の所見は「依頼どおりの案」と並べる第 2 案として出し、否定しない。
19. **遅行指標を成功の定義にしない。** 採用効果のように公開から結果まで長く、Provider が制御できない値は約束できない。成功は Client がその場で判断できる形（方向 2 案から選び修正 2 回で承認）にする。
20. **契約の対象は作業内容。** 準委任でも契約に書くのは作業の範囲・期間・回数上限で、工数は Cost の内側の見積根拠に留める。
21. **依存の検査は機械で回す。** 各 ID の根拠が定義済みか、Contract 以外の各 ID が下流で使われているかをスクリプトで確認してから出す（#3 の機械検査の原型）。
22. **本文に見出し名・ID を書かない。** 「Scope の 2 案」「P-1 を更新」のような参照は提案書のビューで浮く。本文は語で書き、トレースは根拠行と表の備考列に限定して、ビュー生成で落とす。
23. **成果物ごとに読者・目的・形を先に決める。** ビューは計画から根拠を削ったものではなく、読者（決裁者／窓口／Provider）と目的（選んでもらう／承認してもらう／変更を続ける）に合わせて設計した別の形（スライド／1 枚もの／図表先頭の md）。計画は事実と数値を供給するだけ。
24. **人に見せる形は目視で確かめる。** HTML はスクリーンショットを撮って見る。生成が通った＝見られる、ではない（クラス名衝突で額がページ番号の位置に出た）。
25. **追跡用の情報を人の文書に埋め込まない。** ID・根拠列・依存グラフは読む人の視線を奪う。計画は普通の文書として書き、数値の正はデータファイル、依存は見出しの順序で持ち、検査はその外で回す。
26. **前置きを書かない。** 「読者・目的・書式」の説明文は読まれない。文書の形そのもので伝える。
27. **並列は構造、筋道は段落。** 同じ属性が繰り返す項目（体制・工程・リスク・条項・事実の列挙）は表か見出し付き箇条書きにし、理由や判断の筋道だけを段落で書く。全部を表にも全部を段落にもしない。
28. **Discovery は「聞く」でなく「前提を確認する」。** 費用上限・時期・素材・ビルド手順・閲覧環境など、聞けば分かることは先に前提として計画に置き、「違った場合どうするか」を添える。相手は答えやすく、計画は前提が外れた時の動きまで持つ。
29. **方向出し（Direction）は最小の枚数で。** 雰囲気を選ぶ判断材料はトップと本文で足りる。全ページ型 × 端末 × 案数に膨らませると捨てが増え、比較もできない。
30. **対象ページは要素の網羅で機械的に選ぶ。** 直近 N 本を数えて要素の種類が最多のものを選び、足りない要素は Rollout で別ページで確認する。
31. **図はサイト利用者が見るページを起点に、表はそのうち今回触るもの。** 実装単位（テンプレート）起点の図は読者にイメージできない。AsIs に利用者起点の構成図とリンク表、Scope に「触る／触らない」の表。
32. **技術要素は「触る／見た目だけ／触らない」で認識を合わせる。** 触らないものは QA で「見た目を変えても動く・計測が壊れていない」を確認する項目になる。
33. **2 つ以上の話題が並ぶ見出しの下には小見出しを入れる。** 太字ラベルの疑似見出しは構造として読まれない。
34. **出す前に上から通し読みし、初出の語と前後参照を直す。** 未定義の語（共通枠、カンプ、ページ型）、先の節の先取り（2 案、下表）、節間の食い違い（2 回まで／目安）は通し読みでしか見つからない。
35. **事実でない形容を書かない。** 「同業の SIer」「Client 指定」のように、調べていない・入力に無い属性を添えない。選定理由は確認した事実だけで書く。
36. **採用など目的への導線は部品として最重要に扱う。** 目的に直結する部品（採用バナー）は AsIs で事実を押さえ、ToBe で扱いを上げ、Direction の対象に含める。
