# hposal — design notes

Not read at runtime — for whoever maintains the design and needs to judge whether a decision is still
right when requirements change.

（本セッションの決定は D-番号で参照されている。steering.md・dogfood-notes.md からの `D-3` `D-6` `D-9`
`D-10` といった参照はすべてこの文書の各節を指す。）

## 1. Background & Goals

### 1.1 What is the goal?

**決定**：Google Drive にある日本語の読み物キット `corporate-site-kit`（`README.md`＋唯一の手順書
`workflow.md`＋記入用 `templates/` 5本）を、Claude Code から `/hposal:up` として呼び出せるプラグイン
`hposal`（HP proposal）に作り変え、`ccpm` マーケットプレイスに `rn` と並べて `/plugin install` で入る形にする。

**理由**：キットの価値は「HP（コーポレートサイト）の見積・提案書を、要件整理から提案書まで一本道で作らせる
手順」にある。その手順は人が読んで真似るより、AI が上から順に実行する方が速くて漏れがない。プラグイン化は
その手順を「読む文書」から「走る手順」に変える最短経路。

### 1.2 What goes wrong without this?

**決定**：キットが Drive のファイル群のままだと、(a) 使うたびに人が手元へコピーして手順を読み下す必要があり、
(b) 手順の更新が利用者に届かず、(c) 実行のたびに解釈がぶれて成果物の品質が案件ごとに揺れる。

**理由**：手順書は「読まれる」ことを前提にすると必ず読み飛ばされる。⚠️ 落とし穴や★人間ゲートのような
「守られて初めて意味がある」項目ほど飛ばされやすい。プラグインなら手順が実行系に載るので、飛ばしが構造的に
起きにくくなる。

### 1.3 What does reaching it require?

**決定**：(1) `rn` と同じプラグイン構成（`.claude-plugin/plugin.json` / `skills/<name>/SKILL.md` /
`references/` / `README.md` / `CHANGELOG.md`）、(2) 元 `workflow.md` の4フェーズ・共通ルール・全 ⚠️・
★人間ゲートを一つも落とさない移植、(3) `marketplace.json` と root `README.md` への登録、
(4) `claude plugin validate --strict`（plugin / marketplace 両方）の通過、
(5) 実際に回して提案書が出ることの dogfood 検証。

**理由**：(1)–(4) は「入る・壊れていない」ための最低条件だが、それだけでは「使える」ことを保証しない。
このキットの品質は実走してはじめて測れる（フェーズ間で情報が渡るか、★ゲートが分かるか、テンプレが実案件の
変種に耐えるか）。だから dogfood を要件に含める。

### 1.4 What is out of scope?

**決定**：タグ付けと GitHub Release は本セッションで行わない（D-3）。実案件の生データ（クライアント名・
実額・要員）は公開リポジトリに一切持ち込まない（D-4・D-10 の PII 境界）。

**理由**：リリースは `.claude/rules/plugin.md` により「明示のリリース指示があるときだけ」行う別作業。
実案件データは公開マーケットプレイスに置いた時点で取り消せないので、スコープ外ではなく禁止事項として扱う。

## 2. Assumptions & Constraints

### 2.1 What do we take as true?

**決定**：
- 〔事実・確認済〕元キット＝`README.md`＋`workflow.md`（128行）＋`templates/` 5本、すべて日本語。
- 〔事実・確認済〕`rn` がプラグインの型であり、`skills/<フォルダ名>` がそのままコマンド名になる。
- 〔事実・ユーザー確認済〕プラグイン名は `hposal`、読者層は**日本限定**（2026-06-23 確認、D-6 / 4.2）。
- 〔事実・確認済〕元キットの原本は Google Drive にあり読み取り・コピーが可能。だから変換前の比較基準を
  `.rn/hposal-plugin/corporate-site-kit/` に丸ごと持ち込める。

**理由**：この4点はいずれも実物を見て確認した事実で、推測ではない。とくに「読者層＝日本限定」は言語方針
（4.2）の土台なので、`.claude/rules/language.md` の手続き規定どおり作成前にユーザーへ確認して固定した。

### 2.2 What binds the solution?

**決定**：
- **公開マーケットプレイス**である＝実案件データを置けない（4.3）。
- **言語の分岐**：利用者が読む成果物は日本語、AI 向けプロンプトと機械/マーケット向けメタは英語（4.2）。
- **version は `plugin.json` の1か所だけ**（`marketplace.json` には書かない）。
- **`marketplace.json` と root `README.md` は同じ変更内で同期**させる。
- **内容ドリフト禁止**：`workflow.md` の全フェーズ・全ルール・全 ⚠️・★ゲートを保つ。参照の受け渡し点
  （SKILL.md → references）に要約を置かず、ペイロードのみ渡す。
- **最終成果物の形は変えない**：単一 HTML → ヘッドレス Chrome で 16:9 PDF。

**理由**：前4つはリポジトリのルール（`marketplace.md` / `language.md` / `plugin.md`）から来る外的制約。
「内容ドリフト禁止」と「最終成果物の形」は、このセッションが *作り変え* であって *作り直し* ではないことの
表現で、元キットが実案件で効いた部分を失わないための歯止め。

## 3. Design overview

### 3.1 What is the core idea, and why does it solve the problem?

**決定**：**手順は1スキルに一本化**（4.1）し、**成果物テンプレはアウトライン＋パーツに分解**する（4.4）。
前者で「上から順に通す」性質を、後者で「案件ごとの変種」を扱う。

**理由**：問題は2層ある。手順の層は「一本道を飛ばさず通す」ことが価値なので分割しない方が強い。成果物の層は
逆に「案件ごとに違う形が要る」ので、1枚の巨大テンプレを削って手直しするより、変種をパーツとして持ち選択で
組み立てる方が破綻しない。性質をルール（「消し忘れないこと」）でなく構造（選ばなければ存在しない）で担保する。

### 3.2 What are the pieces, and what is each responsible for?

**決定**：
- `hposal/skills/up/SKILL.md` — 4フェーズの手順そのもの（AI 向け指示、英語）。⚠️ と★ゲートの所在地。
- `hposal/references/templates/01_requirements.md` / `02_proposal-design.md` / `03_work-breakdown.md` /
  `site-inventory.md` — 各フェーズの記入用テンプレ（日本語）。
- `hposal/references/templates/04_proposal.md` — 提案書の**アウトライン＝組み立て仕様**（3層の背骨・
  スロット順・各スロットが採るパーツ変種・層→レイアウト・`.pg` 採番）。
- `hposal/references/templates/parts/` — 1パーツ＝1スライドの断片群。`_head.html`（共有 CSS）と
  `_foot.html` が枠、それ以外がスライド本体（種類ごとに変種ファイル）。
- `hposal/.claude-plugin/plugin.json` / `CHANGELOG.md` / `README.md` — メタと入口。
- `.claude-plugin/marketplace.json` エントリ ＋ root `README.md` の一覧行 — 到達経路（機械向けと人間向け）。

**理由**：「手順（SKILL）」「記入する枠（templates）」「組み立て部品（parts）」「メタ」を分ける。SKILL が
どのテンプレを使うかを指すだけにしておけば、テンプレの改訂が手順を書き換えずに済み、逆も同じ。

### 3.3 How does work move?

**決定**：`/hposal:up` を呼ぶと Phase 1（要件整理）→ Phase 2（提案整理）→ Phase 3（作業リスト）→
Phase 4（提案書）を順に進む。各フェーズの出力文書が次フェーズの入力になり、フェーズ境界に★人間ゲートが立つ。
Phase 4 はアウトライン順にパーツを選んで連結し、埋めて、export ゲート（`{{ }}`・見本行の残留ゼロを grep で
機械確認）を通してから PDF に書き出す。

**理由**：依存が一方向の連鎖なので、順序そのものが仕様。★ゲートを境界に置くのは、前フェーズの誤りが後段に
複利で効くため——要件の取り違えは提案書まで行ってから直すと全部やり直しになる。

## 4. Detailed design

### 4.1 D-1: 1スキル `up` で4フェーズ全体を駆動する — 何を保証し、破れをどう検知するか

**保証**：4フェーズが必ず順番に、前フェーズの出力を入力として実行される。フェーズを独立に呼んで依存を
飛ばすことができない。

**決定と理由**：4フェーズを別々のスキル（4コマンド）に割らず、`/hposal:up` 1本に `workflow.md` 全体を載せる。
workflow は★人間ゲートで区切られた一続きの工程で、前フェーズの文書が次の入力になる依存連鎖だから。独立に呼ぶ
4コマンドではなく、上から順に通す1手順として呼ぶのが元キットの使い方に忠実。`rn` が3スキルなのは
start/suspend/resume という独立した3場面があるからで、hposal にはそうした分岐がない。
名前 `up`＝「提案を起こす」を表す短い合図。名前空間 `hposal`（HP proposal）が用途を示すので、コマンド側は
動作の合図で足り、`rn` の短い口語コマンドの流儀に揃う。自己説明性の低さは README 冒頭の一文で補う。

**破れの検知**：フェーズや⚠️の欠落は、元 `workflow.md` との1件ずつの突き合わせ（task #2 で実施、⚠️ 26/26 を
実数確認）で検知する。呼び出せることは `claude -p "/hposal:up" --plugin-dir hposal` のヘッドレス起動で確認。

**根拠**：元キット `workflow.md` 1–10行（「上から順に進める」一本道）・`README.md` 27行（1ファイルを指す）／
お手本 `rn/skills/`／ユーザー確認（`up`＝「起こす」）。

### 4.2 D-6: 言語はプラグインの読者層で分岐する — 何を保証し、破れをどう検知するか

**保証**：利用者が読む成果物は日本語、AI 向けプロンプトと機械/マーケット向けメタは英語、という境界が
ファイル単位で一意に定まる。

**決定と理由**：`hposal` の利用者は「日本語クライアント向け提案を作る日本語話者」に限定される（読者層の確定）。
`language.md` の「読者が一言語に限定されるプラグインは、その利用者が読む成果物をその言語で書く」例外が
そのまま当てはまる。正しい軸は「道具 vs ユーザー接点」ではなく「**プラグインの読者層が一言語に限定されるか**」。
- **日本語**：`hposal/README.md`／`references/templates/` のテンプレ本文（01_requirements・02_proposal-design・
  03_work-breakdown・04_proposal.md・site-inventory）／提案書パーツの記入ガイド・コメント＋クライアント可視
  コピー＋`{{ }}`（提出物そのもの）／実行時生成の中間文書・コンソール会話。
- **英語**：`SKILL.md`（AI 向け作業指示）／`plugin.json`・`marketplace.json` とその description／
  `CHANGELOG.md`／root `README.md` のプラグイン一覧行／コミット・PR 文。

**Audience decision（要・作成前確認）**：`hposal` の読者層＝**日本限定**（2026-06-23 ユーザー確認済）。今後の
プラグインは作成前にこの読者層を確定し、その steering に明示する（`language.md` の手続き規定）。

**破れの検知**：ファイル単位で境界が決まっているので、対象ファイルの言語を目視・grep で判定できる。
`.claude/rules/language.md` の例外節がこの分岐の根拠として repo に常駐している。

**根拠**：ユーザー指示（2026-06-23：「今回のプラグインは利用者が読む成果物は日本語、rn とかは利用者を日本に
限定してない」）。英語化前の日本語原本が `.rn/hposal-plugin/corporate-site-kit/templates/` に現存する。

### 4.3 D-4: スライドHTMLは汎用テンプレ化する — 何を保証し、破れをどう検知するか

**保証**：公開リポジトリに実案件データ（社名・実額・件数・提案者名）が一切残らない。同時に、元 deck の CSS
デザインシステムとレイアウト資産は失われない。

**決定と理由**：完成 deck を雛形にするにあたり、(A) 汎用テンプレ化／(B) 丸ごと見本同梱／(C) 両方 のうち **A**。
CSS とスライド構造は引き継ぎ、固有の中身は `{{ }}` プレースホルダ＋見本行＋記入ガイドに置換する。再利用資産の
本体は CSS とレイアウトであって中身は案件固有だから、B/C は実在クライアントの見積・社名を公開リポジトリに
残すだけで得がない。A なら設計資産を完全継承しつつ実データ流出を避けられる。

**破れの検知**：実データ残留は grep（社名・実額・提案者名）でゼロを機械確認。CSS の温存は元 deck との
byte diff が空であることで確認（分解後は `parts/_head.html` に対して同じ diff を取る）。

**根拠**：元 deck の CSS は実データを含まずコメントも汎用／ユーザー確認（A を選択）／`.claude/rules/marketplace.md`。

### 4.4 D-9: 04 提案書テンプレは「アウトライン＋パーツ（1パーツ1スライド）」 — 何を保証し、破れをどう検知するか

**保証**：案件ごとの変種が「削除・手作り直し・採番ズレ・2列化手術」を経ずに、パーツの**選択**だけで表現できる。
最終成果物は単一 HTML → 16:9 PDF のまま変わらず、CSS はバイト不変。

**決定と理由**：元の `04_proposal.html` は CSS＋20スライドを1ファイルに詰めた 1044行モノリスで、運用は
「`{{ }}` を埋める／要らない任意スライドを削る／`.pg` を手で振り直す」だった。だが dogfood で、各スライドには
本物の変種があり（現状＝単一/複数統合・画面＝サービスCTA/絞り込み検索・見積＝総額/レンジ/複数額比較）、実現手段に
分岐がある案件では比較が“層”として複数スライドにまたがることが分かった。モノリスはこれを「1枚だけ同梱・残りは
削って手で作り直し」「比較は手で2列化」にしてしまい、それが摩擦の正体だった。
そこでテンプレを**アウトライン＋パーツ**に分解する。**1パーツ＝1スライド**（種類ごとに変種ファイル）。
`04_proposal.md` は「3層の背骨・スロット順・各スロットが採るパーツ変種・層→レイアウト（1–2層=1列／3層=2列比較）・
`.pg` は組み立て時採番」を定める**アウトライン＝組み立て仕様**にする。CSS は共有 head パーツ1か所。SKILL フェーズ4は
「アウトライン順にパーツを選び連結→埋める→export」を駆動する。変種を「選択（合成）」に変えることで、性質を
**ルールでなく構造で担保**できる。

**Granularity decision（ユーザー確認）**：1パーツ＝1スライド（2026-06-26 確認済）。ブロック単位（価値カード・
比較行）までは割らない——アウトラインがスライド列に素直に対応し、proposal deck にこの粒度が合うため。

**破れの検知**：代表アウトラインで全パーツを連結→単一 HTML→ヘッドレス Chrome で 16:9 書き出しし、
(a) ページ数と体裁の目視、(b) export ゲート（`{{`・見本行の残留ゼロ）、(c) CSS の byte diff が空、
(d) パーツ網羅（アウトラインの全スロットに対応パーツが存在する）で確認する。

**根拠**：dogfood-notes.md（#10–13・#19・#21）／元モノリス CSS 1–376行は実データを含まずバイト一致で温存できる／
ユーザー確認（2026-06-26）。

### 4.5 D-10: dogfood は実ブリーフ起点・二者構成で回す — 何を保証し、破れをどう検知するか

**保証**：`/hposal:up` が「生ブリーフ1枚 → 完成提案」を実際に導けるかを、自己承認でない独立チェック付きで測る。
かつ実案件の PII が公開リポジトリに戻らない。

**決定と理由**：
- **起点＝実ブリーフ**：施主の生要件だけを残し、前回 dogfood の下流成果物と旧 `dogfood-notes.md` を削除して
  ゼロベースにする。生成物は hposal が要件からいつでも再現できる前提なので完全削除でよい（git 外＝不可逆を承知）。
  dogfood の目的は再現性の検証なので、架空案件より実ブリーフの方が現実の歪みをあぶり出す。
- **二者構成**：subagent が `/hposal:up` を起草実走し、★ゲート/質問で main に返す。main は利用者/レビュー役として
  質問に答え（内部単価など未提供入力は PII なしの仮値を供給）、ドラフトを批判的にレビューして承認/差し戻す。
  ★ゲートと質問機構＝AI↔利用者のやり取りを実際に動かして初めて「AI が訊くべきを訊いたか／ゲートが分かるか」を
  測れる。main 単独の自己起草・自己承認では独立チェックが効かない。

**PII 境界**：実走は private フォルダで行い、生成物 01–04 は private に留める。公開リポジトリ（ccpm）に戻すのは
PII を除いた一般化所見（`dogfood-notes.md`）のみ。

**破れの検知**：所見が周回ごとに `dogfood-notes.md` に積まれ、新所見が出なくなる＝収束したかで手順の安定を測る。
PII 混入は公開側へ戻す前の目視と、実データ語の grep で検知する。

**根拠**：ユーザー指示（2026-06-26）「今の出来では使えないので消して大丈夫／hposal があればいつでも再現できる、
そのためにプラグインを作っている／これから何度も dogfood して再現性を高める」「利用者役は案1（二者構成）」／
`task-execute-workflow.md`（coordinator＝main／implementation expert＝subagent）。

### 4.6 D-3: version は 0.1.0・タグ/Release はスコープ外 — 何を保証し、破れをどう検知するか

**保証**：`--strict` 検証に必要な `version` は存在し、かつ利用者に意図しない更新が配られない。

**決定と理由**：`plugin.json` に `version: 0.1.0` を置く。`--strict` は `version` 未設定を警告のうえ失敗させる
ため必須。一方 `.claude/rules/plugin.md` は「リリース指示があるときだけ昇格・タグはリリース時」と定めるので、
タグ付けと GitHub Release は別の明示指示を待つ。利用者から見ると version を固定するとは「こちらが上げたときだけ
更新が届く」という意味であり、開発中に勝手に配らないための選択でもある。

**破れの検知**：`claude plugin validate hposal --strict` と `claude plugin validate . --strict` の両方が通ること。
`marketplace.json` 側に `version` を書いていないこと（書くと冗長かつ `plugin.json` に負けるので無意味）。

**根拠**：`.claude/rules/plugin.md`。

## 5. Alternatives considered

### 5.1 Why this shape, and not another?

**フェーズごとに4スキルへ割る案**（D-1 の対案）— 不採用。4フェーズは独立した場面ではなく依存連鎖で、
別コマンドにすると「Phase 3 だけ呼んで Phase 2 の出力が無い」を許してしまう。`rn` が3スキルなのは
start/suspend/resume が独立場面だからで、構造が違う。

**言語 = 全部日本語**（旧 D-2）— 撤回。「キットの中身は日本語だから全部日本語」は `language.md` の既定
（成果物は英語）を単に無視しており、AI 向けプロンプトまで日本語にする理由がなかった。

**言語 = 道具は英語／ユーザー接点は日本語**（旧 D-5）— 撤回。この軸で切ると README とテンプレ本文まで英語に
なるが、それを読み・記入するのは日本語話者なので、英語化はコストを上げるだけで到達は広がらない。軸が
「道具 vs ユーザー接点」では粗く、正しい軸は「読者層が一言語に限定されるか」だった（→ 4.2 / D-6）。

**完成 deck を丸ごと見本同梱する案 (B)・汎用化と同梱の両方 (C)**（D-4 の対案）— 不採用。実在クライアントの
見積・社名を公開リポジトリに残すことになる。

**04 テンプレをモノリスのまま運用する案**（D-9 の対案）— 不採用。変種を「削除と手直し」で表現する構造が
採番ズレ・2列化手術・作り直しを生んでいた。ルールで注意させるのではなく、構造から消した。

**パーツをブロック単位（価値カード・比較行）まで割る案**（D-9 の粒度対案）— 不採用。アウトラインが
スライド列に素直に対応しなくなり、組み立てが細かすぎて割に合わない。

**dogfood を main 単独で自己起草・自己承認する案**（D-10 の対案）— 不採用。独立チェックが効かず、
★ゲートと質問機構が実際に働くかを測れない。

**dogfood を架空案件で始める案**（D-10 の対案）— 当初案だったが不採用。実ブリーフの方が現実の歪みを出す。
ただし PII 境界を保てるなら、2周目以降の反復には架空案件を使ってよい（実際 Round 2 はそうしている）。

### 5.2 What did we trade away?

- **組み立ての一手が増えた**（4.4）。モノリスなら1ファイルを開いて埋めるだけだったが、いまはアウトライン順に
  パーツを選んで連結する工程が挟まる。AI が回す前提なので苦にならないと判断した。
- **コマンド名 `up` の自己説明性**（4.1）。短さと `rn` との揃いを取り、説明は README 冒頭の一文に預けた。
- **英語 README による到達の広さ**（4.2）。日本限定という読者層の確定と引き換えに手放した。読者層が変われば
  この決定は見直す必要がある。
- **前回 dogfood の生成物**（4.5）。git 外で完全削除したので復元できない。「hposal があれば要件から再現できる」
  という前提が崩れると取り返せない——その前提自体が dogfood で検証している対象でもある。
- **タグ / Release による版の可視性**（4.6）。本セッション中は「どのコミットがどの版か」がタグから読めない。
