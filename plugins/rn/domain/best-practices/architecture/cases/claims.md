# Claims, a pass on every question

[The Claims architecture](../examples/claims.md), a web product of five containers in the cloud,
with three systems outside it. It's a kept case of the [architecture best
practice](../best-practice.md): a deliverable with the verdict on each question that someone who
knows the developer's work gives, so that an evaluator proves itself on it before anyone trusts its
verdicts. It's also one of the best practice's examples, so this file holds its verdicts alone.

## Verdicts

| Question | Verdict | Why |
| --- | --- | --- |
| Q1 | yes | Three use cases carry the README's steps, and six ranked scenarios each end in a measure, such as 95% of requests within one second. The records and the principles name the scenarios they answer. |
| Q2 | yes | Context, five containers, and the components of the two containers that hold more than one decision. The web app holds one and gets no component level. |
| Q3 | yes | The core and the policy depend on nothing outside the standard library, six ports each name a real adapter and a test's, and `go-arch-lint` checks the rule on each push. |
| Q4 | yes | Each of the six relations names what crosses, its form, its owner, and where its contract lies, and the concept model names each data alike in every view. |
| Q5 | yes | Each use case draws its branches, the refused photo, the manager who doesn't approve, the provider that fails, and the drop that's down. |
| Q6 | yes | The browser, the cluster, and the cloud account, each with what it runs or keeps, the outside systems, how CI deploys, and how a developer runs it on their computer. |
| Q7 | yes | The opening gives the idea of one service and an outbox, the two principles carry their reasons, and each record gives its context, the option it beat, and its consequences. |
| Q8 | yes | No line says how a component works inside. The retries and the minute's delay are drivers' measures and a record's consequence, and a change to the SQL of the repository leaves every line true. |
| Q9 | yes | The unit level takes the states of a Claim and the policy's rules alone. The integration level runs the real database with doubles only at Identity, Mail, and Drop, and a nightly contract test keeps them true. |
| Q10 | yes | Each path of the three runtime views has its integration test, named before any code. |
| Q11 | yes | A new developer can follow `U2` from its driver through every section, and each element and data keeps its name across the figures, the tables, and the tests. |
