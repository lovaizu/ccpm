# Changelog

## [Unreleased]

### Added

- The lanes your AI proposes, in one JSON file in the form docs/lanes.md gives, are shown by `lay.py print` with each lane under the action it watches, its hook, each adapter run on its cases and each step as it will read, and once approved written by `lay.py write` from the same file: each lane's sentence at the end of its step, the lanes in `hooks/lanes.json`, one hook entry of your plugin for each event, your other hooks left as they were, the adapters in `hooks/adapters/` and Lane's code in `hooks/lane/`, after which `claude plugin validate` runs and the proposal and its adapters are removed — what runs is what you approved, and nothing is copied by hand.
- Laid again, a step loses the sentence of each lane no longer laid on it, in whichever words Lane laid it, has a sentence in words Lane laid before put in its current words, and the hooks of a subagent your plugin no longer has are taken out — what your subagent reads in its step is always what its hooks check.
- The run_only lane stops a subagent running any command but those its step names, each matched whole, and tells it `<plugin>: Run only <commands>.` with the commands it may run on the next line — the subagent goes back to its step instead of looking for another way round the refusal.
- The write_only lane stops a subagent writing any file but the outputs its step names, by the path Write, Edit or NotebookEdit is given, and tells it `<plugin>: Write only <output>.` — the rest of your project stays as it was.
- The read_only lane stops a subagent reading any file but the inputs its step names, by the path Read or Grep is given, and tells it `<plugin>: Read only <input>.`, letting it read the form its in_form lane names and its own part — it works from what its step gives it, not from what it happened to find.
- The in_form lane holds a write of an output its step names to the form the step names, a JSON Schema of the keywords Anthropic's structured outputs accept or a Markdown template's headings and frontmatter keys, before the write is made and again as the subagent gives its result, and tells it `<plugin>: Write <output> in the form of <form>.` with the point that is out on the next line — the next step does not meet a file out of its form.
- The edit_only lane lets a Write make an output its step names while it is not there, and once it is, stops a Write or NotebookEdit of it and tells the subagent `<plugin>: Once <output> is made, change it only with Edit.`; Claude Code lets an Edit go only after a Read of the file — a subagent sees each part it changes, as in a design tree whose nesting holds what each part serves.
- The hold lane answers Claude Code to ask the person before a command its step names runs, with `<plugin>: Run <commands> only with the person's approval.`, so Claude Code's own permission prompt puts it to them, even under `bypassPermissions`; in `claude -p` no one can be asked and Claude Code refuses the command — nothing you must approve runs without you, and Lane approves nothing in your place.
- The read_whole, test_after, end_when and every_item lanes are checked as the subagent runs its result command, from the calls Lane kept: an input its Read calls did not cover to its end, an output changed with no test passed after, an output not made, or an item of an input, read at the items port, whose ID stands in no file it wrote in this run, stops the command with each lane's sentence and what is missing on the next line; a subagent with one of them and no route gives the result `done` — work handed on is whole, read through, tested and answered.
- Routes, written under the proposal's `routes` as docs/routes.md gives them, have Lane tell your orchestrator each next start as it starts and as each start comes back, a start counting once its subagent, run in the background, has ended; any other start is stopped, the orchestrator is kept going once while a start is due and then let end, you told what is left and whose step to fix, and a subagent about to end without a result is kept going once with the sentence of its last step — the order of your subagents follows your routes with no script of yours.
- A subagent gives its result by running the result script Lane puts into your plugin, `python3 ${CLAUDE_PLUGIN_ROOT}/hooks/lane/result.py <subagent> <result>`, which exits with an error naming the results it may give where no route is on it, and Lane keeps the result only from a run that succeeded — a reply such as "No more entries" is never read as `more`.
- A lane may take a thing given for each run, written `{<name>}`, the value under that name read at the values port from the prompt of the Agent call that started the subagent and each message a SendMessage call sent to it after, the later over the earlier, the prompt kept under the `agentId` the call gives back, so runs of one subagent at once are each held to their own; a value given as `null` lets the lane through on that run — one sentence holds a subagent to the files of each run, a file added by a message held from then on.
- `lay.py print` refuses a subagent with lanes, or named by your routes, whose file does not set `background: true`, and the hook stops each call of one whose file no longer does — every run goes in the background, your conversation stays free, runs that stand apart go at once, and each is told from the others by the ID its start gives back.
- A run_only, hold or test_after lane may name a command of a dependency's skill, writing the folder Claude Code installed the dependency in as `${dependency:<name>}`: that part is any folder holding the manifest of the plugin of that name, which your plugin's own manifest declares in its `dependencies`, and the rest is matched whole — your subagent runs the scripts of the plugins yours depends on, and nothing else in their place.
- Routes may name in `fan_out` the subagents your orchestrator may start several runs of at once, each run with its own prompt and values; the route is taken once every run has ended, from the result they share or, where they differ, the first of them in the order your routes give in `precedence`, which `lay.py print` asks of each subagent fanned out with more than one result — work split over runs at once goes on by one result, by your plugin's own order.
- A run_only, hold or test_after command may hold a value given for the run as one part, such as `python3 ${CLAUDE_PLUGIN_ROOT}/scripts/check.py {file}`, the rest matched whole and the value put in as one word of the shell, quoted where it holds a blank or another character of the shell — a command runs on each run's own file, and no value adds a word to it.
- A path of a read_only, write_only or read_whole lane may begin with `${CLAUDE_PLUGIN_ROOT}`, and Lane puts your plugin's folder in for it, as in a command — a step holds its subagent to a file of your plugin, such as how it is to work, by the path it reads it by.
- A subagent's part may lie under your plugin's `core/roles/` as well as `prompts/`, found by the name its entry's body gives — a role's flow kept apart from Claude Code is read, shown and laid as a part is.
- Where your plugin writes a text in another form than Lane reads, an adapter of yours, a Python 3 script with the cases it must give, is approved with the proposal, run on its cases before it is printed, and run by the hook within its time — Lane holds your plugin in the form it writes in, with no lane made for it.
- A subagent whose entry names its part, one file under your plugin's `prompts/`, has its steps read from the part, shown by `lay.py print`, laid there by `lay.py write`, and is given the part whole as it starts, your plugin's folder put in — your subagent has its steps before its first call, and subagents sharing a part share one set of sentences.
- What Lane cannot check is stopped, or the subagent kept going once as it ends, and it and you are told `<plugin>: lane cannot check <lane> on step <n> of <subagent>: <what is wrong>.` with who must fix it, such as a value not given, an adapter failing, a step no longer saying its sentence or a form gone — nothing passes unchecked, and you know whose fix it is.
- Without Python 3.9 or later run as `python3`, each tool call of a subagent with lanes is stopped, and the subagent and you are told to install it — a lane is never left unkept with no one told.
- `lay.py up` brings an older copy of Lane's code in your plugin and its hook entries up to Lane's version, puts each sentence a step says in words Lane laid before in Lane's current words, the rest of the step as it was, and says each lane and adapter laid before, for your AI to keep in its proposal — your lanes keep working across Lane's updates, and none you approved is dropped unsaid.
