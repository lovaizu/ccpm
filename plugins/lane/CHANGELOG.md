# Changelog

## [Unreleased]

### Added

- The hands_off lane stops a subagent running a command its step says not to run, in the forms the AI writes, such as `git -C notes commit`, `cd notes && git commit` or `GIT_EDITOR=true git commit`, and tells it `<plugin>: Do not run <commands>.` — the subagent goes back to its step instead of looking for another way round the refusal.
- The start_with lane stops each call a subagent makes before it has run the script its step says to run first, the script taken as the step writes the command, such as `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/turn.py" start`, and tells it `<plugin>: First run <script>.` — the subagent begins from what the script gives it, not from what it looked for on its own.
- The read_only lane stops a subagent reading a file beside the inputs its step names, by the Read or Grep tool or by `cat`, `head`, `tail`, `sed` or `grep`, and tells it `<plugin>: Read only <input>.`, letting it read the form its in_form lane names; a command naming a file by words lane cannot settle, such as `cat "$f"` or a relative path after a `cd` it cannot follow, is stopped the same, with a line saying lane cannot tell which file it is and to name it by its path — it works from what its step gives it, not from what it happened to find, still reads the form its step tells it to write in, and no read goes through unchecked.
- The read_whole lane stops a subagent writing while it has read only part of an input its step names, read from what it has done since it started, and tells it `<plugin>: Read <input> to its end.` — it does not act on the first part of a long input alone.
- The write_only lane stops a subagent writing any file but the outputs its step names, with Write, Edit or NotebookEdit, or in the folder it works in with a command, such as a redirect, `tee`, `cp`, `mv` or `sed -i`, and tells it `<plugin>: Write only <output>.`; a command naming a file by words lane cannot settle, such as `> "$out"` or a relative path after a `cd` it cannot follow, is stopped the same, with a line saying lane cannot tell which file it is and to name it by its path — the rest of your project stays as it was, the subagent goes back to writing what its step names, and no write goes through unchecked.
- The in_form lane stops a subagent writing an output its step names out of the form the step names, before the write is made: JSON, or JSONL line by line, held to a JSON Schema of the keywords Anthropic's structured outputs accept, or Markdown held to a template's headings and frontmatter keys; it tells `<plugin>: Write <output> in the form of <form>.`, the form named by a path the subagent can read, with the one point that is out on the next line, its place, what was expected and what was found — the subagent puts that point right, and the next step does not meet a file out of its form.
- The test_after lane keeps a subagent going as it is about to end when its last change to an output its step names has no passing run of the test after it, and tells it `<plugin>: After changing <output>, pass <test>.` — a change does not reach you untested; a run passes only where its exit is the test's, so `; echo exit=$?` after a failing test does not count.
- The as_printed lane stops each call a subagent makes, once a command its step names has printed, until it hands on what the command last printed, word for word with one heading line allowed, as an Agent call's prompt or a SendMessage's message, and keeps it going when it is about to end with a last reply that holds none of it, telling it `<plugin>: Hand on <command> as it is.` — what reaches the next agent or you is what the command printed, not the subagent's retelling of it, and before the subagent acts on anything else.
- The follow_next lane stops a subagent's calls, once a script its step names has printed the next move, read at the move port, by default as one JSON line `{"tool": ..., "input": {...}}`, until it takes that move, and keeps it going when it is about to end before taking it, telling it `<plugin>: Take the next move <script> printed.` — the run goes where your script sends it, and does not stop partway.
- The wait_for lane stops a subagent running a command its step holds back until a message holding the approval, such as `OK`, has reached it since it last asked, and tells it `<plugin>: Do not go on until <approval>.`; `lay.py print` shows the commands it holds back beside its hook — nothing you have to approve goes on before you have.
- The end_when lane keeps a subagent going as it is about to end when it has not made the output its step names in this run, and tells it `<plugin>: End only once <output> is made.` — a file left from an earlier run does not stand in for the work.
- The every_item lane keeps a subagent going as it is about to end when an item of an input its step names, read at the items port, by default a top-level list item keyed by an ID such as `B-1`, is named neither in its last reply nor in a file it wrote, and tells it `<plugin>: Answer every item of <input>.` — no finding is dropped unanswered.
- A lane may take a thing given for each run, written `{<name>}` in its step, such as `{work}`: the value under that name the values port reads in what the subagent is given, by default the JSON of its prompt, of what the script start_with runs first prints or of a message sent to it after, the later over the earlier, a list standing for each of its texts; a drift is told with the sentence as the step says it and the run's value on the next line, the lane is held once the script start_with runs has run and come back, the call that runs it let through, and a value given as `null` lets each call and the end through on that run, with nothing told — a subagent whose files differ on each run is held to the files of its own run, a file added while it works, as by an answer, is held from the message that adds it with no new start of the subagent, and a run that has none of them is said so by its caller rather than stopped.
- Each lane reads your plugin's text at a port lane defines, the values, the items of an input or the move a script printed, each by the JSON it is given and gives back; where your text is in another form than lane's, an adapter of your plugin's, a Python 3 script with the cases it must give, is approved with the proposal, run on its cases before it is printed, and written into `hooks/adapters/` — lane holds your plugin in the form it writes in, with no lane of its own made for it.
- What each lane is given is held to the lane's IN, a JSON Schema docs/lanes.md shows, as the lanes are laid and on every run; a value not given or given empty, an adapter failing, the record not found, a step no longer saying its lane's sentence, or a form in_form names gone since it was laid is an error, the call stopped, or the subagent kept going once as it ends, and it and you told `<plugin>: lane cannot check <lane> on step <n> of <subagent>: <what is wrong>.`, or `<plugin>: lane cannot check the lanes of <subagent>: <what is wrong>.` where the event or `hooks/lanes.json` is what is wrong, headed `lane:` where the hook's command does not name the subagent as `lay.py write` writes it, with who must fix it — what lane cannot check is stopped and told rather than let through unchecked, and a wrong take shows when the lanes are laid.
- Each hook `lay.py write` lays on a tool call blocks the call where it fails to start, exits other than 0 or 2, times out or prints no JSON Claude Code reads, by `"onFailure": "block"` (Claude Code 2.1.295 or later) — a call lane could not check is stopped rather than let through unchecked.
- A subagent told by a lane at its end and answering in words alone, with no call since, is let end — it is told, never held for good, and its reply reaches the one who started it.
- The lanes your AI proposes, in a JSON file in the shape docs/lanes.md gives, are shown by `lay.py print`, each under the action it watches with its hook and the step as it would read, and once approved written into your plugin by `lay.py write` from the same file, word for word, the sentence at the end of its step, the lanes themselves in `hooks/lanes.json`, a thing taken holding any text, and one hook for each subagent and event in `hooks/hooks.json`, naming the subagent alone, your other hooks left as they were, with lane's code in `hooks/lane/`; laid again, the sentence of each lane no longer laid on a step is taken out of it, and the hooks of a subagent your plugin no longer has are taken out of `hooks/hooks.json` — what your subagent is told on a drift is the sentence its step says, and no hook is left for you to remove by hand.
- `lay.py up`, run where an older copy of lane's code is, brings the copy and its hooks up to lane's version with the same lanes, and says each lane laid before, for your AI to keep in its proposal, lay another way or leave out — your lanes keep working across lane's updates, and none you approved is dropped unsaid.
- Without Python 3.9 or later run as `python3`, each hook on a tool call stops the calls it watches and asks for Python to be installed, and each hook at a subagent's end tells you so and lets the subagent end, each answering in Claude Code's JSON output as every hook of lane's does — a lane is never left unkept with no one told, and a subagent is not kept going on what it cannot put right.
- A subagent whose file is its entry, its frontmatter and a body having it read its part in `prompts/` first, has its steps read from that part, shown by `lay.py print`, laid there by `lay.py write` and read there by the guard, and, once lanes are laid in it, is held to read the part whole before anything else, a Read of it let through and any other call before it is read to its end stopped and told the entry's own sentence — your plugin can keep each subagent's Role and Steps in a file named for its part, and the subagent works from them whole rather than from what it guessed first.
- A subagent's entry can say where each script, file or folder its part names lies, as `` `turn.py` below is `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/turn.py"` ``, and each lane taking the name, such as start_with, follow_next or in_form, holds the subagent to the one the entry names, its sentence showing the name as the step says it — your part names things by name alone and runs wherever Claude Code installs your plugin, as Claude Code puts the plugin's folder in for `${CLAUDE_PLUGIN_ROOT}` in the entry alone.
- An adapter is run with `CLAUDE_PLUGIN_ROOT` set to your plugin's folder, beside the proposal as in your plugin — an adapter can hand your text to a module of your plugin and still be tried on its cases before it is laid.
