# rn 設計書

## rn が実現すること

- ざっくりしたゴールから、ユーザーが本当に欲しいものを一緒に詰める。
- そこから先はユーザー抜きで進め、ユーザーが決めることだけをサインオフで聞く。
- context がいっぱいになっても、`/clear` しても、翌日でも、push 済みのブランチから続けられる。

## 作るものはすべて、本質的な観点で作り、同じ観点で確かめる

```mermaid
flowchart TD
    E(["essentials.md:<br/>作るものごとの観点"])
    M["指揮者か生成者:<br/>作って、セルフチェックする"]
    V["指揮者、評価者:<br/>確かめる、評価する"]
    C["指揮者: 決める"]
    E -->|"狙い"| M
    E -->|"問い"| V
    M -->|"作ったもの"| V
    M -->|"Good と More"| C
    V -->|"Good と More"| C
```

手順は渡さない。手順は字面どおりに守られて、状況が想定と違うと的を外し、書いた人の想定までしか届かない。観点なら、磨くほど `rn` が良くなり、動かすモデルが良くなるほど得をする。

Good は狙いに役立っていて残すべきもの、More は届いていないところと、そのせいで読む人に何がまずいか、どう直すか。

`rn` を良くするときは essentials.md を磨く。文書の書き方は essentials.md に持たず、ユーザーが入れている書き方のスキルやルールに従う。

## 指揮者が決め、生成者が作り、作っていない評価者が評価する

```mermaid
flowchart TD
    U(["ユーザー"])
    C["メインの会話の指揮者"]
    G["タスクごとに立つ生成者"]
    E["評価ごとに立つ評価者"]
    U -->|"会話、コマンド"| C
    C -->|"問い、根拠を添えたサインオフ"| U
    C -->|"タスク、直す More"| G
    G -->|"作業ツリーの編集、セルフチェック"| C
    C -->|"評価するコミットか文書"| E
    E -->|"評価"| C
```

- 次の一手を決めるのも、git を使うのも、指揮者だけ。

  作業を頼んだ者が、それが目的に届くことに責任を持つ。評価の字面どおりに動くと、ゴールに役立っている作業までやり直すことになる。

- 評価者には、ユーザーが合意したことと言ったことだけを渡し、どう作ったかは渡さない。

  作った人の見方は自分の理由に寄るので、作っていない人がユーザーの立場で見る。

- ユーザーが決めるのは、好み、範囲、費用対効果、プロダクトのあるべき姿、収束しないやり方、成果物がゴールに届いたかだけ。

  それ以上を聞くと、ユーザーは作業を任せきれなくなる。

## 文書が作業を先導し、今の状態だけを持つ

```mermaid
flowchart TD
    U(["ユーザー"])
    C["指揮者"]
    G["生成者"]
    E["評価者"]
    S["steering.md:<br/>進め方"]
    RD["README と設計書:<br/>あるべき姿と作り方"]
    O["open/:<br/>まだ片付いていない項目"]
    M["コミットメッセージ:<br/>判断の1行と、片付いた項目"]
    C -->|"書く"| S
    C -->|"ユーザーと詰めて書く"| RD
    G -->|"セルフチェック"| O
    E -->|"評価"| O
    U -->|"/rn:gm の言葉"| O
    C -->|"/rn:dn のメモ"| O
    O -->|"指揮者が決めて片付ける"| M
```

- 進め方も作り方もあるべき姿も文書の上で議論し、文書は作業より先に変わる。
- 文書には経緯を書かず、経緯はコミットメッセージが運ぶ。

  文書に経緯を残すと、今成り立っていることが埋もれる。

- 片付いた項目は、そのコミットで `open/` から消え、空になったファイルも消える。

  残っている項目は指揮者が要るか要らないかを決めるので、何も漏れない。サインオフで止まるときは、いつも空。

- 生成者は `steering.md`、README、設計書を読み、評価者はそのうちユーザーが合意したところを読む。ユーザーは全部をプルリクエストで読む。
- `steering.md` の項目と `open/` のファイル名は、後の版の `rn` も読む約束。

  `steering.md` の項目は、そのひな形が持つ。`open/` のファイル名は `{NN}-{kind}-{about}.md` で、kind は `check`、`evaluation`、`feedback`、`notes`。

## セッションの流れ

```mermaid
flowchart TD
    ON(["/rn:on"])
    W["ゴールをユーザーと詰める"]
    P["次の判断までの計画を作り、<br/>評価する"]
    PS{{"Plan サインオフ"}}
    T["タスクを1つずつ進める"]
    D["設計をユーザーと詰めて<br/>README と設計書に書き、評価する"]
    DS{{"Design サインオフ"}}
    P2["続くタスクを計画し、評価する"]
    EV["成果物を評価する"]
    T2["評価から足したタスクを進める"]
    FS{{"Deliverable サインオフ"}}
    END(["プルリクエストを ready にする"])
    ON --> W --> P --> PS
    PS -->|"/rn:ty"| T
    T -->|"ユーザーが決めることが出た"| D
    D --> DS
    DS -->|"/rn:ty"| P2
    P2 --> T
    T -->|"タスクがすべて済んだ"| EV
    EV -->|"足すタスクがある"| T2
    T2 --> FS
    EV -->|"足すタスクがない"| FS
    FS -->|"/rn:ty"| END
```

- 計画は次の判断までしか立てない。

  判断の先に立てたタスクは、判断が下るとほとんど書き直しになる。

- `/rn:ty` はサインオフを閉じて止まり、次のステップは「続けて」か `/rn:up` で始まる。
- `/rn:gm` は、サインオフで見せたものをユーザーの言葉どおりに直し、同じサインオフで止まる。

  直しは指揮者が確かめ、それに答えるのは評価者ではなくユーザー。

- `/rn:dn` はどこでも一時停止し、`/rn:up` はそこから次のサインオフまで進める。

  以前の `rn` で始めたセッションは、`/rn:up` が古い記録からゴールを詰め直し、新しい Plan サインオフで止まる。

## 作るもの1つの流れ

```mermaid
flowchart TD
    M["生成者がタスクの成果を作る"]
    K{"指揮者が目的に照らして確かめる"}
    C["コミットして push"]
    V["評価者が評価する"]
    KE{"指揮者が評価を確かめる"}
    O["評価を open/ に置いて push"]
    D{"指揮者が More を1つずつ決める"}
    F["生成者が直す"]
    FK{"指揮者が直しを確かめる"}
    S["片付いた More をメッセージに入れて<br/>コミットして push"]
    U["済んでいないタスクの代わりに<br/>Design サインオフへ"]
    M --> K
    K -->|"届いていない"| M
    K -->|"届いた"| C
    C --> V
    V --> KE
    KE -->|"根拠がない、<br/>目的から外れている"| V
    KE -->|"妥当"| O
    O --> D
    D -->|"直す"| F
    F --> FK
    FK -->|"届いていない"| F
    FK -->|"届いた"| S
    D -->|"見送る"| S
    D -->|"ユーザーが決めること"| U
```

- 計画と設計も同じ流れで、作って直すのが指揮者になる。成果物は「評価者が評価する」から始まる。
- More は、直せば目的に近づくか、直しても Good が保たれるかで決める。

  互いに食い違う More は、ゴール、観点、文書のどこかに決まっていないことがあるしるしなので、片方を選ばず、そこで決める。

- ゴールから決められない More は、ユーザーに渡す。

  README や設計書を変える直しも、収束しないやり方も含む。同じ More が繰り返し出るときや、直すたびに新しい More が出るときが、収束しないやり方。

- 評価は1回で、直しはもう一度評価しない。

  何回評価するかは本来は指揮者が決めることだが、AI だけで評価を回すと本質的でない指摘が続いて収束しないので、今は1回評価したら指揮者とユーザーが決める。
